## 0. 🗺️ Общая картина: как устроен конвейер

Прежде чем настраивать, полезно понимать, что именно мы строим.

**Непрерывная интеграция (CI, Continuous Integration)** — автоматическая проверка каждого изменения кода. Цель: поймать ошибку до того, как она попадёт в основную ветку.

**Непрерывная доставка (CD, Continuous Delivery/Deployment)** — автоматическая упаковка и доставка проверенного кода на сервер. Цель: убрать ручные действия, в которых человек ошибается.

Схема того, что будет собрано:

```
                    ┌─────────────────────────────────────────┐
   git push  ──────►│ CI: линтеры → сборка → дымовой тест     │  (раздел 7)
   в main или PR    └─────────────────────────────────────────┘
                                    │
                                    ▼
                          изменение принято в main
                                    │
   git tag v1.0.0                   ▼
   git push --tags   ┌─────────────────────────────────────────┐
        ────────────►│ CD, шаг 1: сборка образа → ghcr.io      │  (раздел 8)
                     └─────────────────────────────────────────┘
                                    │
                                    ▼
                     ┌─────────────────────────────────────────┐
                     │ CD, шаг 2: SSH на VPS → pull → запуск   │  (раздел 10)
                     └─────────────────────────────────────────┘
                                    │
                                    ▼
                          страница доступна в сети
```

**Ключевая идея разделения:** обычная отправка кода запускает только проверки — это быстро и безопасно. Развёртывание запускается **только созданием тега**. Тег — это осознанное решение человека «вот эта версия идёт в работу». Так случайный коммит не уедет на боевой сервер.

## 2. 🐳 Установка и настройка Docker Engine

- **Что:** Среда контейнеризации, состоящая из фонового сервиса (Docker Daemon) и интерфейса командной строки (Docker CLI).
- **Где:** Внутри операционной системы Ubuntu (WSL 2).
- **Почему:** Контейнеры позволяют упаковать приложение вместе со всеми зависимостями и окружением. Это гарантирует одинаковую работу приложения как на локальной машине, так и на продакшен-сервере (VPS).

### Шаг 2.1. Установка с официального скрипта

- **Зачем:** Скрипт `get.docker.com` подтягивает самые актуальные версии Docker Engine и плагина Docker Compose из официальных репозиториев Docker, минуя устаревшие пакеты из системного дистрибутива.
- **Как:**

```bash
curl -fsSL https://get.docker.com -o get-docker.sh
sudo sh get-docker.sh
```

### Шаг 2.2. Настройка прав (безопасность и удобство)

- **Зачем:** По умолчанию управлять демоном Docker может только пользователь `root`. Чтобы не писать `sudo` перед каждой командой, текущего пользователя добавляют в системную группу `docker`.
- **Как:**

```bash
# Добавляем текущего пользователя ($USER) в группу docker
sudo usermod -aG docker $USER

# Обновляем права группы для текущей сессии bash без перезагрузки
newgrp docker
```

### Шаг 2.3. Проверка работы

- **Зачем:** Убедиться, что Docker Daemon запущен, а текущий пользователь имеет к нему доступ.
- **Как:**

```bash
docker run --rm hello-world
```

- `docker run` — команда создания и запуска контейнера.
- `--rm` — автоматически удаляет контейнер из памяти после его остановки (не оставляет «мусора»).

## 3. 📦 Инициализация системы контроля версий (Git)

- **Что:** Распределенная система контроля версий.
- **Где:** В локальной папке проекта `~/projects/git-navigator`.
- **Почему:** Позволяет отслеживать изменения в коде, возвращаться к предыдущим состояниям (микро-коммиты как точки сохранения) и синхронизировать работу с удаленными репозиториями.

### Команды и параметры

```bash
# Инициализация нового Git-репозитория (создает скрытую папку .git)
git init

# Проверка статуса отслеживаемых и неотслеживаемых файлов
git status

# Добавление всех файлов текущей директории в staging area (подготовка к коммиту)
git add .

# Фиксация изменений в истории
# Важно: флаг -m пишется без пробела после дефиса!
git commit -m "Сообщение коммита"
```

## 4. 🛠️ Упаковка приложения в Docker (Dockerfile)

- **Что:** Текстовый файл-инструкция для сборки Docker-образа (Docker Image).
- **Где:** Корень проекта (`~/projects/git-navigator/Dockerfile`).
- **Почему:** Вместо ручной установки Nginx и копирования файлов мы описываем этот процесс в коде (Infrastructure as Code).

### Содержимое Dockerfile

```dockerfile
# Использование легкого базового образа Nginx на базе Alpine Linux (весит около 20 МБ)
FROM nginx:alpine

# Копирование локального файла статики в стандартный каталог раздачи Nginx
COPY index.html /usr/share/nginx/html/

# Документирование порта, который использует контейнер
EXPOSE 80
```

### Сборка и запуск

```bash
# Сборка образа с тегом (именем) git-navigator:v1.0
# Точка в конце обозначает контекст сборки (текущая директория)
docker build -t git-navigator:v1.0 .

# Локальный запуск контейнера
docker run -d -p 8080:80 --name my-cheat-sheet git-navigator:v1.0
```

- **Разбор флагов `docker run`:**
  * `-d` (*detached*) — запуск контейнера в фоновом режиме.
  * `-p 8080:80` (*port mapping*) — проброс порта. `8080` — порт на хосте (WSL), `80` — порт внутри контейнера, который слушает Nginx.
  * `--name` — человекочитаемое имя контейнера.

```bash
# Проверка работы веб-сервера
curl http://localhost:8080

# Остановка и удаление тестового контейнера
docker stop my-cheat-sheet
docker rm my-cheat-sheet
```

## 5. 🔑 Авторизация на GitHub и SSH-ключи (GitHub CLI)

- **Что:** Утилита `gh` (GitHub CLI) для управления репозиториями из терминала и протокол авторизации SSH.
- **Где:** Ubuntu (WSL) ⟷ GitHub.com.
- **Почему:** SSH предоставляет защищенное соединение на основе пары ключей (приватный/публичный). Это позволяет безопасно отправлять код на GitHub без ввода пароля при каждом `push`.

### Авторизация через `gh`

```bash
gh auth login
```

- **Выбранные параметры:**
  1. **Where do you use GitHub?** → `GitHub.com`
  2. **Preferred protocol:** → `SSH`
  3. **Generate SSH Key:** → `Yes` (автоматически генерирует современный ключ `Ed25519` и загружает его публичную часть на GitHub).
  4. **Authentication method:** → `Paste an authentication token` (использование Personal Access Token с правами `repo`, `admin:public_key`).

### Проверка состояния авторизации

```bash
gh auth status
```

Пример реального вывода после успешной настройки:

```text
~/projects/git-navigator$ gh auth status
github.com
  ✓ Logged in to github.com account novi4ok-ai (/home/kornik/.config/gh/hosts.yml)
  - Active account: true
  - Git operations protocol: ssh
  - Token: ghp_************************************
  - Token scopes: 'admin:enterprise', 'admin:gpg_key', 'admin:org', 'admin:org_hook',
    'admin:public_key', 'admin:repo_hook', 'admin:ssh_signing_key', 'audit_log',
    'codespace', 'copilot', 'delete:packages', 'delete_repo', 'gist', 'notifications',
    'project', 'repo', 'user', 'workflow', 'write:discussion',
    'write:network_configurations', 'write:packages'
```

- **Как читать вывод:**
  * `✓ Logged in to ... account novi4ok-ai` — авторизация активна. Зелёная галочка `✓` означает успех; крестик `✗` означает, что токен отсутствует, истёк или отозван.
  * `(/home/kornik/.config/gh/hosts.yml)` — файл, в котором `gh` хранит учётные данные. Именно его нужно проверять при проблемах с авторизацией.
  * `Active account: true` — этот аккаунт выбран как активный. Параметр важен, если через `gh auth login` добавлено несколько аккаунтов (например личный и рабочий).
  * `Git operations protocol: ssh` — операции `push`/`pull` идут по SSH. Это следствие выбора `SSH` на шаге авторизации; при значении `https` Git будет требовать токен вместо ключа.
  * `Token: ghp_****...` — токен всегда маскируется звёздочками, поэтому такой вывод безопасно показывать и сохранять в документации. Посмотреть значение целиком можно командой `gh auth token`, но её вывод — секрет.
  * `Token scopes` — список прав, выданных токену.

> ⚠️ **О правах токена:** в примере выше выдан очень широкий набор, включая `admin:org`, `admin:enterprise` и `delete_repo` — такой токен позволяет удалять репозитории и управлять организацией. Для задач этого руководства достаточно `repo` и `admin:public_key`. По принципу наименьших привилегий стоит выпустить отдельный токен только с нужными правами: [github.com/settings/tokens](https://github.com/settings/tokens).

## 6. 🐙 Публикация репозитория на GitHub

- **Что:** Связывание локального репозитория с удаленным сервисом GitHub.
- **Где:** Из WSL в облако GitHub.
- **Почему:** Для хранения бэкапов кода и, самое главное, для запуска CI/CD автоматизации (GitHub Actions) при каждом обновлении кода.

### Команда создания и публикации

```bash
gh repo create --source=. --public --remote=origin --push
```

- **Разбор параметров:**
  * `--source=.` — использовать текущую папку в качестве источника кода.
  * `--public` — создать публичный репозиторий.
  * `--remote=origin` — задать стандартный псевдоним `origin` для URL-адреса удаленного репозитория.
  * `--push` — автоматически выгрузить все локальные коммиты ветки `main` на GitHub сразу после создания.

```bash
# Проверка настроенных удаленных адресов
git remote -v
```

## 7. ✅ Непрерывная интеграция: линтеры и дымовой тест

> **Статус: ⬜ требует проверки**

- **Что:** Автоматический набор проверок, запускаемый на серверах GitHub при каждом изменении кода.
- **Где:** Файл `.github/workflows/ci.yml` в репозитории; выполняется на одноразовой виртуальной машине GitHub.
- **Почему:** Человек забывает проверить руками. Машина не забывает никогда. Проверки ловят опечатки, неправильную разметку и неработающую сборку до того, как код попадёт в основную ветку.

### Терминология GitHub Actions

Перед написанием файла — четыре понятия, без которых дальше будет непонятно:

| Термин | Что это |
|---|---|
| **Рабочий процесс** (workflow) | Файл `.yml` в папке `.github/workflows/`. Одна автоматизация. |
| **Событие** (trigger, блок `on:`) | Что запускает процесс: отправка кода, создание тега, запрос на слияние. |
| **Задание** (job) | Изолированная виртуальная машина. Задания по умолчанию идут параллельно. |
| **Шаг** (step) | Одна команда или одно готовое действие внутри задания. |

**Действие** (action) — переиспользуемый блок из чужого репозитория, подключается через `uses:`. Например `actions/checkout@v6` — это репозиторий `github.com/actions/checkout`, ветка/тег `v6`.

### Шаг 7.1. Проверка линтеров локально

- **Зачем:** Ключевой принцип — в конвейере запускается ровно та же команда, что и на локальной машине. Тогда результат воспроизводим и нечему «разъезжаться». Поэтому линтеры берутся контейнерами, а не сторонними действиями.
- **Как:** По одной команде, смотрим вывод каждой.

```bash
# Проверка Dockerfile на типовые ошибки и небезопасные конструкции
docker run --rm -i hadolint/hadolint < Dockerfile
```

```bash
# Проверка синтаксиса самих файлов рабочих процессов
docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:latest -color
```

```bash
# Проверка разметки HTML
npx --yes html-validate index.html
```

Файл настроек для проверки разметки (чтобы поведение было одинаковым везде):

```bash
cat > .htmlvalidate.json <<'EOF'
{
  "extends": ["html-validate:recommended"]
}
EOF
```

- **Что означает пустой вывод:** ошибок нет. Это норма для `hadolint` и `actionlint`.
- **Типовые замечания `html-validate` на скорую руку написанной странице:** отсутствует атрибут `lang` у тега `html`, отсутствует `<meta charset="utf-8">`, отсутствует `<title>`. Всё это исправляется в `index.html` за минуту.

### Шаг 7.2. Файл рабочего процесса проверок

- **Где:** `.github/workflows/ci.yml`

```bash
mkdir -p .github/workflows
nano .github/workflows/ci.yml
```

```yaml
name: ci

# Событие: отправка в main и любой запрос на слияние в main
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

# Права встроенного токена. Меньше прав — меньше ущерб при взломе.
permissions:
  contents: read

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - name: Забрать код репозитория
        uses: actions/checkout@v6

      - name: Проверить Dockerfile
        run: docker run --rm -i hadolint/hadolint < Dockerfile

      - name: Проверить файлы рабочих процессов
        run: docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:latest -color

      - name: Проверить разметку HTML
        run: npx --yes html-validate index.html

  smoke:
    runs-on: ubuntu-latest
    needs: lint          # запустится только после успешного задания lint
    steps:
      - name: Забрать код репозитория
        uses: actions/checkout@v6

      - name: Собрать образ
        run: docker build -t git-navigator:test .

      - name: Запустить контейнер
        run: docker run -d --name smoke -p 8080:80 git-navigator:test

      - name: Дымовой тест — страница отдаётся и не пустая
        run: |
          curl -fsS --retry 10 --retry-delay 1 --retry-connrefused \
            http://localhost:8080 -o page.html
          grep -q "<title>" page.html

      - name: Убрать контейнер
        if: always()     # выполнится даже если предыдущий шаг упал
        run: docker rm -f smoke
```

**Разбор неочевидных мест:**

- **`needs: lint`** — задания выполняются последовательно, а не параллельно. Смысл: не тратить время и ресурсы на сборку образа, если код не прошёл базовую проверку.
- **`--retry-connrefused` у `curl`** — контейнер поднимается не мгновенно. Без повторных попыток тест периодически падает без реальной причины. Это самая частая причина «мигающих» тестов, которые проходят через раз.
- **`-fsS` у `curl`** — `-f` возвращает ненулевой код при ответе сервера 4xx/5xx (без него `curl` считает успехом даже страницу «404»), `-s` убирает индикатор загрузки, `-S` оставляет вывод ошибок.
- **`if: always()`** — уборка выполняется в любом случае. На одноразовой машине GitHub это некритично, но привычка правильная: на собственном сервере сборки мусорные контейнеры накапливаются.

**Что такое дымовой тест (smoke test):** минимальная проверка «включается ли вообще». Название пришло из электроники: собрал плату, подал питание — если дыма нет, можно проверять дальше. Здесь то же самое: собрали образ, запустили, страница отдалась — базовая работоспособность подтверждена.

### Шаг 7.3. Отправка и проверка

```bash
git add .github/workflows/ci.yml .htmlvalidate.json
git commit -m "ci: линтеры и дымовой тест"
git push
```

```bash
# Список последних запусков
gh run list --limit 3

# Наблюдение за текущим запуском в реальном времени
gh run watch

# Журнал упавшего запуска (только ошибочные шаги)
gh run view --log-failed
```

### Шаг 7.4. Сделать проверки обязательными

- **Зачем:** Сам по себе проваленный набор проверок ничего не запрещает — код всё равно можно влить в `main`. Защита ветки делает успешное прохождение обязательным условием слияния.
- **Как:** Настройки репозитория → Branches → Add branch ruleset → для `main` включить «Require status checks to pass» и выбрать задания `lint` и `smoke`.

## 8. 📤 Сборка и публикация образа по тегу

> **Статус: ⬜ требует проверки**

- **Что:** Рабочий процесс, который по созданию тега собирает образ и кладёт его в реестр контейнеров GitHub (ghcr.io).
- **Где:** Файл `.github/workflows/release.yml`.
- **Почему:** Образ — это неизменяемый артефакт. Один раз собран, дальше только копируется. Это гарантирует, что на сервере окажется ровно то, что прошло проверки, а не пересобранное заново с другими версиями зависимостей.

### Почему именно тег, а не отправка в main

Тег — явный маркер версии. Правило именования — семантическое версионирование:

```
v МАЖОРНАЯ . МИНОРНАЯ . ПАТЧ
  │          │          └── исправления, обратная совместимость сохранена
  │          └───────────── новая функциональность, совместимость сохранена
  └──────────────────────── ломающие изменения
```

Из тега `v1.4.2` конвейер сам сделает метки образа `1.4.2`, `1.4` и `latest`.

### Шаг 8.1. Файл рабочего процесса

```bash
nano .github/workflows/release.yml
```

```yaml
name: release

# Событие: отправка тега, начинающегося с буквы v
on:
  push:
    tags:
      - 'v*'

permissions:
  contents: read       # читать код
  packages: write      # писать в реестр образов

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    outputs:
      # Пробрасываем вычисленный номер версии в следующее задание (раздел 10)
      version: ${{ steps.meta.outputs.version }}
    steps:
      - name: Забрать код репозитория
        uses: actions/checkout@v6

      - name: Подготовить сборщик Buildx
        uses: docker/setup-buildx-action@v4

      - name: Войти в реестр ghcr.io
        uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Вычислить имя и метки образа
        id: meta
        uses: docker/metadata-action@v6
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}

      - name: Собрать и опубликовать образ
        uses: docker/build-push-action@v7
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

**Разбор неочевидных мест:**

- **`secrets.GITHUB_TOKEN`** — временный токен, который GitHub создаёт сам на время запуска и уничтожает после. В настройки репозитория его добавлять не нужно, он существует всегда. Права токена задаются блоком `permissions`.
- **`docker/metadata-action`** — вычисляет метки образа из имени тега. Метку `latest` добавляет самостоятельно, когда видит тег по правилам семантического версионирования. Отдельная строка для неё не нужна.
- **`cache-from` / `cache-to: type=gha`** — слои сборки сохраняются в кеш GitHub. Повторные сборки идут в разы быстрее, потому что неизменившиеся слои не пересобираются.
- **Версии действий** указаны актуальные: `checkout@v6`, `login-action@v4`, `setup-buildx-action@v4`, `metadata-action@v6`, `build-push-action@v7`. Более старшие мажорные версии работают на Node.js 20, который с серверов сборки убирают в сентябре 2026 года.

### Шаг 8.2. Создание тега

**Критично: порядок действий.** Файл рабочего процесса должен уже находиться в коммите, на который указывает тег. Иначе тег отправится, а запускать будет нечего — файла в том состоянии кода ещё не существует.

```bash
git add .github/workflows/release.yml
git commit -m "ci: сборка и публикация образа по тегу"
git push

# Аннотированный тег: содержит автора, дату и сообщение
git tag -a v1.0.0 -m "Первый релиз"

# Теги не уезжают вместе с обычным push, их отправляют отдельно
git push origin v1.0.0
```

- **Аннотированный (`-a`) против простого:** простой тег — это просто указатель на коммит. Аннотированный — полноценный объект в базе Git с автором, датой и сообщением. Для версий используется только аннотированный.

### Шаг 8.3. Проверка результата

```bash

```

Проверка, что образ реально лежит в реестре и запускается:

## 9. 🖥️ Ручная подготовка VPS

> **Статус: ⬜ требует проверки**

- **Что:** Разовая настройка удалённого сервера: пользователь, ключи доступа, отключение входа по паролю, Docker.
- **Где:** Виртуальный сервер (VPS) с Ubuntu 24.04.
- **Почему:** Этот раздел выполняется руками один раз. Автоматизировать создание самого сервера нельзя без доступа к личному кабинету провайдера, а всё остальное после первичной настройки делает конвейер.

### Шаг 9.1. Первый вход и создание рабочего пользователя

- **Зачем:** Работать под `root` опасно: любая ошибка в команде необратима, а любой процесс получает полные права. Создаётся отдельный пользователь с возможностью повышения прав через `sudo`.

```bash
# Первый вход по данным от провайдера
ssh root@АДРЕС_СЕРВЕРА

# Создание пользователя (запросит пароль и необязательные данные)
adduser deploy

# Право повышать привилегии
usermod -aG sudo deploy
```

### Шаг 9.2. Ключи доступа для администратора

- **Зачем:** Пароль можно подобрать перебором. Ключ длиной 256 бит перебрать нельзя. Схема: приватная часть остаётся на локальной машине и никуда не уходит, публичная кладётся на сервер.
- **Где выполняется:** На локальной машине (WSL), **не на сервере**.

```bash
# Создание пары ключей. -N "" означает пустую парольную фразу
ssh-keygen -t ed25519 -f ~/.ssh/vps_admin -C "admin@git-navigator"

# Копирование публичной части на сервер (последний раз спросит пароль)
ssh-copy-id -i ~/.ssh/vps_admin.pub deploy@АДРЕС_СЕРВЕРА
```

- **`ed25519`** — современный алгоритм на эллиптических кривых. Ключ короче и быстрее устаревшего RSA при большей стойкости.

Чтобы не вводить адрес и путь к ключу каждый раз, добавляется запись в файл настроек клиента SSH:

```bash
nano ~/.ssh/config
```

```
Host my-vps
    HostName 203.0.113.10
    User deploy
    IdentityFile ~/.ssh/vps_admin
    IdentitiesOnly yes
```

```bash
chmod 600 ~/.ssh/config

# Теперь вход выполняется одной короткой командой
ssh my-vps
```

- **`IdentitiesOnly yes`** — предлагать серверу только указанный ключ. Без этого клиент перебирает все имеющиеся ключи и сервер может разорвать соединение, исчерпав лимит попыток.

### Шаг 9.3. Отключение входа по паролю

- **Зачем:** Пока вход по паролю разрешён, сервер круглосуточно перебирают автоматические сканеры. Отключение убирает этот класс атак полностью.
- **Критично:** Перед выполнением **держи открытым второй сеанс SSH**. Если в настройках окажется ошибка, а действующий сеанс будет закрыт, доступ к серверу будет потерян и останется только консоль в панели провайдера.

```bash
# На сервере
sudo nano /etc/ssh/sshd_config.d/99-hardening.conf
```

```
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
```

- **Почему отдельный файл, а не правка `sshd_config`:** в Ubuntu основной файл содержит строку подключения каталога `sshd_config.d`. Отдельный файл переживает обновление пакета и сразу видно, что именно было изменено вручную.

```bash
# Проверка синтаксиса ДО применения. Пустой вывод — ошибок нет
sudo sshd -t

# Применение
sudo systemctl reload ssh
```

Проверка из **нового** окна терминала:

```bash
ssh my-vps            # должен пустить по ключу
ssh -o PreferredAuthentications=password deploy@АДРЕС   # должен отказать
```

### Шаг 9.4. Установка Docker на VPS

Те же команды, что в разделе 2, но выполняются на сервере:

```bash
curl -fsSL https://get.docker.com -o get-docker.sh
sudo sh get-docker.sh

sudo usermod -aG docker deploy
```

Права группы применяются при новом входе:

```bash
exit
ssh my-vps
docker run --rm hello-world
```

### Шаг 9.5. Отдельный ключ для конвейера

- **Зачем:** Личный административный ключ в настройки GitHub не кладут никогда. Для автоматики создаётся отдельная пара. Если она скомпрометирована — отзывается одной строкой, личный доступ при этом не затронут.
- **Где:** Создаётся на локальной машине.

```bash
# Пустая парольная фраза обязательна: конвейер не сможет её ввести
ssh-keygen -t ed25519 -f ~/.ssh/gh_deploy -C "github-actions@git-navigator" -N ""
```

```bash
# Публичная часть добавляется на сервер
cat ~/.ssh/gh_deploy.pub | ssh my-vps 'cat >> ~/.ssh/authorized_keys'

# Проверка, что новый ключ работает
ssh -i ~/.ssh/gh_deploy -o IdentitiesOnly=yes deploy@АДРЕС_СЕРВЕРА 'docker --version'
```

### Шаг 9.6. Передача данных в секреты репозитория

- **Что такое секрет:** зашифрованное значение в настройках репозитория. Конвейер получает его при запуске, в журналах оно автоматически заменяется звёздочками.

```bash
# Из папки проекта на локальной машине
gh secret set VPS_HOST --body "203.0.113.10"
gh secret set VPS_USER --body "deploy"

# Приватный ключ читается из файла, а не набирается руками
gh secret set VPS_SSH_KEY < ~/.ssh/gh_deploy

# Отпечаток сервера — чтобы конвейер знал, к кому подключается
gh secret set VPS_KNOWN_HOSTS --body "$(ssh-keyscan -t ed25519 203.0.113.10 2>/dev/null)"

# Проверка списка
gh secret list
```

- **Зачем `VPS_KNOWN_HOSTS`:** без него придётся отключать проверку отпечатка сервера флагом `StrictHostKeyChecking=no`. Это открывает возможность подмены сервера посредником. Правильный путь — заранее сохранить настоящий отпечаток.

## 10. 🚀 Автоматическое развёртывание на VPS

> **Статус: ⬜ требует проверки**

- **Что:** Задание, которое после успешной публикации образа подключается к серверу по SSH и перезапускает контейнер новой версии.
- **Где:** Дополнение к файлу `.github/workflows/release.yml`.
- **Почему:** Это последнее ручное звено. После его автоматизации выпуск версии — одна команда `git push origin v1.0.1`.

### Шаг 10.1. Задание развёртывания

Добавляется в конец `release.yml`, после задания `build-and-push`:

```yaml
  deploy:
    runs-on: ubuntu-latest
    needs: build-and-push          # только после успешной публикации образа
    environment: production        # позволяет включить ручное подтверждение
    steps:
      - name: Подготовить ключ и отпечаток сервера
        run: |
          mkdir -p ~/.ssh
          chmod 700 ~/.ssh
          echo "${{ secrets.VPS_SSH_KEY }}" > ~/.ssh/id_ed25519
          chmod 600 ~/.ssh/id_ed25519
          echo "${{ secrets.VPS_KNOWN_HOSTS }}" > ~/.ssh/known_hosts
          chmod 644 ~/.ssh/known_hosts

      - name: Развернуть новую версию
        env:
          VPS_HOST: ${{ secrets.VPS_HOST }}
          VPS_USER: ${{ secrets.VPS_USER }}
          IMAGE: ghcr.io/${{ github.repository }}:${{ needs.build-and-push.outputs.version }}
        run: |
          ssh -o IdentitiesOnly=yes "$VPS_USER@$VPS_HOST" "IMAGE='$IMAGE' bash -s" <<'REMOTE'
          set -euo pipefail
          docker pull "$IMAGE"
          docker rm -f git-navigator 2>/dev/null || true
          docker run -d \
            --name git-navigator \
            --restart unless-stopped \
            -p 80:80 \
            "$IMAGE"
          docker image prune -f
          REMOTE

      - name: Проверить, что сайт отвечает
        env:
          VPS_HOST: ${{ secrets.VPS_HOST }}
        run: |
          curl -fsS --retry 10 --retry-delay 2 --retry-connrefused \
            "http://$VPS_HOST/" -o /dev/null
```

**Разбор неочевидных мест:**

- **Секреты через `env`, а не прямо в команде.** Если подставлять `${{ secrets.X }}` в текст команды, значение попадает в строку скрипта. Через `env` оно передаётся переменной окружения — это защищает от подстановки постороннего кода и является общепринятой практикой.
- **`needs.build-and-push.outputs.version`** — номер версии, вычисленный из тега в предыдущем задании. Разворачивается конкретная версия, а не подвижная метка `latest`. Известно точно, что именно работает на сервере.
- **`<<'REMOTE'` в одинарных кавычках** — содержимое блока не разворачивается на машине сборки, а передаётся на сервер как есть. Переменная `$IMAGE` подставляется уже там, потому что передана через `IMAGE='...' bash -s`.
- **`set -euo pipefail`** — скрипт на сервере останавливается на первой же ошибке. Без этого неудачное получение образа не помешает продолжить и сломать работающий контейнер.
- **`docker rm -f ... || true`** — при первом развёртывании контейнера с таким именем ещё нет. Без `|| true` шаг упал бы на пустом месте.
- **`--restart unless-stopped`** — контейнер поднимется сам после перезагрузки сервера.
- **`docker image prune -f`** — удаление старых неиспользуемых образов. Без этого диск VPS постепенно заполняется.
- **`environment: production`** — именованное окружение. В настройках репозитория (Settings → Environments) ему можно назначить обязательное подтверждение человеком: конвейер дойдёт до развёртывания и остановится, ожидая нажатия кнопки.

### Шаг 10.2. Выпуск версии

```bash
git add .github/workflows/release.yml
git commit -m "cd: развёртывание на VPS по тегу"
git push

git tag -a v1.0.1 -m "Проверка автоматического развёртывания"
git push origin v1.0.1

gh run watch
```

Затем — открыть `http://АДРЕС_СЕРВЕРА` в браузере.

## 11. 🔄 Проверка цепочки и откат версии

> **Статус: ⬜ требует проверки**

### Полная проверка конвейера

| Действие | Ожидаемый результат |
|---|---|
| Изменить `index.html`, отправить в отдельную ветку, открыть запрос на слияние | Запускается `ci`, оба задания зелёные |

| Исправить, слить в `main` | `ci` проходит, `release` **не** запускается |
| Создать и отправить тег `v1.0.2` | Запускается `release`, образ публикуется, сайт обновляется |

### Откат на предыдущую версию

- **Зачем:** Автоматическое развёртывание ценно ровно настолько, насколько быстро можно вернуться назад. План отката продумывается заранее, а не в момент аварии.

**Способ 1 — вручную на сервере (быстро, секунды):**

```bash
ssh my-vps

docker run -d --name git-navigator --restart unless-stopped -p 80:80 \
  ghcr.io/ВАШ_ЛОГИН/git-navigator:1.0.1
```

Возможность отката существует именно потому, что каждая версия опубликована под собственной неизменяемой меткой. Это главный практический аргумент против развёртывания метки `latest`.

**Способ 2 — через конвейер (правильно, минуты):** исправить код и выпустить новый тег `v1.0.3`. Состояние сервера остаётся описанным в репозитории.

## 12. 📋 Сводная шпаргалка

### Итоговая структура проекта

```
git-navigator/
├── .github/
│   └── workflows/
│       ├── ci.yml              # проверки при отправке кода и запросах на слияние
│       └── release.yml         # сборка, публикация и развёртывание по тегу
├── .htmlvalidate.json          # настройки проверки разметки
├── Dockerfile                  # описание образа
├── index.html                  # содержимое страницы
└── SETUP_GUIDE.md              # этот файл
```

### Ежедневный цикл работы

```bash
# 1. Работа над изменением
git switch -c feature/новое-описание
nano index.html
git add . && git commit -m "feat: обновлён текст страницы"
git push -u origin feature/новое-описание

# 2. Запрос на слияние — конвейер проверок запускается сам
gh pr create --fill
gh pr checks --watch

# 3. Слияние после успешных проверок
gh pr merge --squash --delete-branch

# 4. Выпуск версии
git switch main && git pull
git tag -a v1.0.3 -m "Обновление текста"
git push origin v1.0.3
gh run watch
```

### Полезные команды диагностики

```bash
gh run list --limit 5              # последние запуски
gh run view --log-failed           # журнал только упавших шагов
gh run rerun --failed              # перезапустить упавшие задания
gh secret list                     # какие секреты заданы
git tag -l                         # список локальных тегов
git push origin --delete v1.0.0    # удалить тег на GitHub
git tag -d v1.0.0                  # удалить тег локально
```

### Типовые ошибки и их причины

| Симптом | Причина | Решение |
|---|---|---|
| Тег отправлен, ничего не запустилось | Файла рабочего процесса нет в коммите, на который указывает тег | Сначала отправить файл в `main`, затем создавать тег |
| `denied: permission_denied` при публикации образа | Не задан блок `permissions: packages: write` | Добавить блок в файл рабочего процесса |
| `Host key verification failed` | Секрет `VPS_KNOWN_HOSTS` пустой или неверный | Перезаписать выводом `ssh-keyscan` |
| `Permission denied (publickey)` при развёртывании | Приватный ключ передан не полностью, либо публичная часть не добавлена на сервер | Перезаписать секрет через `gh secret set VPS_SSH_KEY < файл` |
| Дымовой тест падает через раз | Контейнер не успевает подняться | Повторные попытки у `curl` (`--retry-connrefused`) |
| Порт 80 занят на VPS | На сервере уже работает веб-сервер | Остановить его либо изменить проброс порта |
| Диск VPS заполняется | Накапливаются старые образы | `docker image prune -f` в скрипте развёртывания |

### Словарь понятий

| Понятие | Значение |
|---|---|
| **CI** | Непрерывная интеграция. Автоматическая проверка каждого изменения кода. |
| **CD** | Непрерывная доставка. Автоматическая упаковка и доставка проверенного кода. |
| **Конвейер** (pipeline) | Вся цепочка от изменения кода до работающего приложения. |
| **Артефакт** | Результат сборки. Здесь — образ контейнера. Неизменяем. |
| **Реестр** (registry) | Хранилище образов. Здесь — `ghcr.io`. |
| **Линтер** | Программа статической проверки без выполнения кода. |
| **Дымовой тест** | Минимальная проверка базовой работоспособности. |
| **Секрет** | Зашифрованное значение в настройках репозитория, скрытое в журналах. |
| **Семантическое версионирование** | Схема `МАЖОРНАЯ.МИНОРНАЯ.ПАТЧ` для номеров версий. |

### Направления развития шпаргалки

Что логично добавить, когда базовая цепочка отработана:

1. **Обратный прокси-сервер** (Caddy или Traefik) — автоматические сертификаты HTTPS.
2. **Развёртывание без простоя** — сейчас между остановкой старого контейнера и запуском нового проходит секунда-две недоступности.
3. **Файл `docker-compose.yml` на сервере** — когда сервисов станет больше одного.
4. **Закрепление действий по контрольной сумме коммита** вместо мажорной версии — защита от подмены стороннего действия.
5. **Автоматическое обновление зависимостей** (Dependabot) — следит за выходом новых версий действий.
6. **Проверка образа на уязвимости** (Trivy) отдельным шагом перед публикацией.
