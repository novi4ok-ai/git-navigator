# 📘 CI/CD с нуля: от пустой папки до автоматического развёртывания

Практическое руководство. Простейший пример — HTML-страница в контейнере — доведён до полноценного конвейера: проверки кода, сборка образа, публикация, развёртывание на сервере, откат.

Материал рассчитан на того, кто раньше не настраивал автоматизацию. Каждый шаг объясняется и проверяется.

---

## Как читать это руководство

Каждый шаг оформлен одинаково:

- **Что это** — объяснение понятия.
- **Зачем** — какую задачу решает и что случится без этого.
- **Сделай** — команда или файл.
- **Ожидаемый результат** — как понять, что получилось.
- **Если пошло не так** — типовая причина сбоя.

Выполняй по порядку. Каждая часть опирается на предыдущую.

### Карта руководства

| Часть | Тема | Что получишь в конце |
|---|---|---|
| I | Локальное окружение | Страница работает в контейнере на своей машине |
| II | Теория CI/CD | Понимание, что и зачем автоматизируется |
| III | Первая автоматизация | Простейший рабочий процесс запускается на серверах GitHub |
| IV | Проверки кода | Каждое изменение автоматически проверяется |
| V | Выпуск версии | По тегу собирается и публикуется образ |
| VI | Развёртывание | По тегу новая версия уезжает на сервер |
| VII | Эксплуатация | Умеешь откатываться и находить причину сбоя |

### Отметки о прохождении

Отмечай части по мере выполнения — так руководство остаётся честным при возврате к нему через полгода.

| Часть | Статус |
|---|---|
| I. Локальное окружение | ⬜ |

# ЧАСТЬ I. ЛОКАЛЬНОЕ ОКРУЖЕНИЕ

Цель части: получить работающую страницу в контейнере на своей машине и связать проект с GitHub.

---

## 1. Подготовь среду выполнения — WSL 2

**Что это.** Подсистема Windows для Linux. Настоящее ядро Linux внутри Windows, без тяжёлой виртуальной машины.

**Зачем.** Все инструменты автоматизации рассчитаны на Linux. Серверы сборки GitHub тоже работают на Linux. Работая в WSL, ты выполняешь ровно те же команды, что потом выполнит автоматика — и не ловишь расхождения между своей машиной и сервером.

**Сделай.** Создай рабочую папку проекта:

```bash
mkdir -p ~/projects/git-navigator
cd ~/projects/git-navigator
pwd
```

**Ожидаемый результат.** Команда `pwd` печатает путь вида `/home/твоё_имя/projects/git-navigator`.

---

## 2. Установи Docker

**Что это.** Среда контейнеризации. Состоит из фонового сервиса (Docker Daemon), который управляет контейнерами, и командной строки (Docker CLI), через которую ты им управляешь.

**Зачем.** Контейнер упаковывает приложение вместе с окружением: операционной системой, веб-сервером, файлами. Один и тот же контейнер работает одинаково на твоём ноутбуке, на сервере сборки и на боевом сервере. Это устраняет главную причину сбоев при развёртывании — «на моей машине работало».

### Шаг 2.1. Установи движок

**Зачем именно так.** Скрипт `get.docker.com` — официальный. Он подключает репозитории Docker и ставит свежие версии. Пакет `docker.io` из стандартных репозиториев Ubuntu обычно отстаёт на несколько версий.

**Сделай:**

```bash
curl -fsSL https://get.docker.com -o get-docker.sh
sudo sh get-docker.sh
```

Разбор флагов `curl` — они будут встречаться дальше постоянно:
- `-f` — вернуть ошибку, если сервер ответил кодом 4xx/5xx. Без него в файл может записаться страница с ошибкой.
- `-s` — не показывать индикатор загрузки.
- `-S` — но ошибки всё же показывать.
- `-L` — переходить по перенаправлениям.
- `-o имя` — сохранить в файл.

**Ожидаемый результат.** Длинный вывод установки, в конце — сообщение о завершении.

### Шаг 2.2. Дай себе права без sudo

**Зачем.** По умолчанию управлять Docker может только `root`. Каждая команда потребует `sudo`. Добавление в системную группу `docker` снимает это неудобство.

**Сделай:**

```bash
sudo usermod -aG docker $USER
newgrp docker
```

- `usermod -aG docker $USER` — добавить текущего пользователя в группу `docker`. Флаг `-a` означает «добавить, не убирая из других групп». Пропустишь его — пользователь вылетит из всех остальных групп.
- `newgrp docker` — применить новую группу прямо сейчас, без перезахода в систему.

**Ожидаемый результат.** Приглашение командной строки вернулось, ошибок нет.

### Шаг 2.3. Проверь, что всё работает

**Сделай:**

```bash
docker run --rm hello-world
```

- `docker run` — создать и запустить контейнер.
- `--rm` — удалить контейнер сразу после остановки, не оставляя мусора.

**Ожидаемый результат.** Docker скачает крошечный образ и напечатает текст, начинающийся со слов о том, что установка работает корректно.

**Если пошло не так.** Ошибка о невозможности подключиться к сокету означает, что сервис не запущен: выполни `sudo service docker start`.

## 3. Заведи систему контроля версий

**Что это.** Git — распределённая система контроля версий. Хранит историю всех состояний проекта.

**Зачем.** Без истории нельзя вернуться назад. И без Git не работает ничего из последующих частей: вся автоматизация запускается именно событиями Git — отправкой кода, созданием тега.

### Шаг 3.1. Представься Git

**Зачем.** Каждый коммит подписывается именем и почтой. Без настройки Git откажется фиксировать изменения.

**Сделай:**

```bash
git config --global user.name "Имя Фамилия"
git config --global user.email "почта@example.com"

# Основную ветку по умолчанию назвать main, а не master
git config --global init.defaultBranch main

git config --global --list
```

**Ожидаемый результат.** Последняя команда печатает заданные значения.

### Шаг 3.2. Создай репозиторий

**Сделай:**

```bash
cd ~/projects/git-navigator
git init
git status
```

- `git init` — создать скрытую папку `.git` с базой истории.
- `git status` — показать, какие файлы Git видит и в каком они состоянии.

**Ожидаемый результат.** Сообщение о создании пустого репозитория, затем — что коммитов пока нет.

### Шаг 3.3. Создай страницу

**Зачем именно такая разметка.** На следующих шагах разметку будет проверять автоматика. Здесь сразу заложено то, чего она требует: язык страницы, кодировка, заголовок.

**Сделай:**

```bash
cat > index.html <<'EOF'
<!DOCTYPE html>
<html lang="ru">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Git Navigator</title>
</head>
<body>
  <h1>Git Navigator</h1>
  <p>Версия развёрнута автоматически.</p>
</body>
</html>
EOF
```

Конструкция `cat > файл <<'EOF' ... EOF` записывает в файл всё до строки `EOF`. Кавычки вокруг `EOF` означают «не подставлять переменные, писать как есть».

**Ожидаемый результат.** Проверь командой `cat index.html` — она покажет содержимое.

### Шаг 3.4. Зафиксируй первое состояние

**Сделай:**

```bash
git add .
git commit -m "Первая версия страницы"
git log --oneline
```

- `git add .` — пометить все файлы текущей папки к включению в следующий коммит. Эта промежуточная область называется индексом.
- `git commit -m "текст"` — записать помеченное в историю. Флаг `-m` задаёт сообщение прямо в команде.
- `git log --oneline` — компактная история.

**Ожидаемый результат.** Одна строка с коротким номером коммита и твоим сообщением.

## 4. Упакуй страницу в контейнер

**Что это.** `Dockerfile` — текстовая инструкция по сборке образа. Образ — это шаблон, из которого создаются контейнеры.

**Зачем.** Вместо описания словами «поставь nginx, положи файл туда-то» ты описываешь это кодом. Инструкция лежит рядом с проектом, версионируется вместе с ним и выполняется одинаково у всех.

### Шаг 4.1. Создай Dockerfile

**Сделай:**

```bash
cat > Dockerfile <<'EOF'
# Базовый образ: nginx на Alpine Linux, около 20 МБ
FROM nginx:alpine

# Копирование страницы в каталог, который nginx раздаёт по умолчанию
COPY index.html /usr/share/nginx/html/

# Отметка о том, какой порт слушает контейнер.
# Порт не открывается автоматически — это документация для человека и инструментов
EXPOSE 80
EOF
```

**Разбор инструкций:**
- `FROM` — от какого готового образа отталкиваемся. Всегда первая инструкция.
- `COPY источник назначение` — скопировать файл из папки проекта внутрь образа.
- `EXPOSE` — объявление порта. Реальный проброс делается при запуске флагом `-p`.

### Шаг 4.2. Добавь файл исключений

**Что это.** `.dockerignore` — список того, что не попадёт в контекст сборки.

**Зачем.** При сборке Docker передаёт содержимое папки своему движку. Без исключений туда уедет вся история Git, служебные файлы редактора, документация. Это замедляет сборку и раздувает образ.

**Сделай:**

```bash
cat > .dockerignore <<'EOF'
.git
.github
*.md
.htmlvalidate.json
node_modules
EOF
```

### Шаг 4.3. Собери образ

**Сделай:**

```bash
docker build -t git-navigator:local .
```

- `-t имя:метка` — присвоить образу имя и метку.
- `.` в конце — контекст сборки, то есть папка, из которой брать файлы. Точку забывают чаще всего.

**Ожидаемый результат.** Несколько строк с шагами сборки, в конце — сообщение об успешной записи образа.

Проверь список образов:

```bash
docker images | grep git-navigator
```

### Шаг 4.4. Запусти и проверь

**Сделай:**

```bash
docker run -d -p 8080:80 --name test-page git-navigator:local
```

- `-d` — запуск в фоне, терминал освобождается.
- `-p 8080:80` — проброс порта. Слева порт на твоей машине, справа порт внутри контейнера.
- `--name` — человекочитаемое имя вместо случайного.

**Проверь:**

```bash
docker ps
curl http://localhost:8080
```

**Ожидаемый результат.** `docker ps` показывает строку с контейнером `test-page` в состоянии `Up`. `curl` печатает разметку страницы.

**Убери за собой:**

```bash
docker rm -f test-page
```

Флаг `-f` останавливает и удаляет одной командой.

## 5. Настрой доступ к GitHub

**Что это.** `gh` — официальная командная строка GitHub. SSH — протокол защищённого соединения на паре ключей.

**Зачем.** Пара ключей состоит из приватной части (остаётся у тебя навсегда) и публичной (кладётся на сервер). Сервер проверяет, что ты владеешь приватной частью, не получая её. Пароль при отправке кода больше не нужен.

**Сделай:**

```bash
gh auth login
```

Отвечай на вопросы:
1. **Where do you use GitHub?** → `GitHub.com`
2. **Preferred protocol** → `SSH`
3. **Generate a new SSH key?** → `Yes` (создаст современный ключ Ed25519 и сам загрузит публичную часть на GitHub)
4. **How would you like to authenticate?** → вход через браузер либо вставка личного токена доступа с правами `repo`, `admin:public_key`

**Проверь:**

```bash
gh auth status
ssh -T git@github.com
```

**Ожидаемый результат.** Первая команда подтверждает вход. Вторая приветствует тебя по имени и сообщает, что оболочка по SSH не предоставляется — это нормальный ответ, означающий успех.

## 6. Опубликуй репозиторий

**Зачем.** Автоматизация GitHub Actions работает только с кодом на GitHub. Пока репозиторий локальный, запускать нечего.

**Сделай:**

```bash
gh repo create --source=. --public --remote=origin --push
```

- `--source=.` — взять текущую папку.
- `--public` — публичный репозиторий. Для публичных репозиториев автоматизация бесплатна без ограничений по времени.
- `--remote=origin` — назвать удалённый адрес стандартным именем `origin`.
- `--push` — сразу отправить существующие коммиты.

**Проверь:**

```bash
git remote -v
gh repo view --web
```

**Ожидаемый результат.** Первая команда покажет адрес вида `git@github.com:логин/git-navigator.git`. Вторая откроет репозиторий в браузере.

# ЧАСТЬ II. ТЕОРИЯ: ЧТО ТАКОЕ CI/CD

Прежде чем настраивать, разберись в понятиях. Иначе дальше будет копирование без понимания.

---

## 7. Разберись в понятиях

### Непрерывная интеграция (CI)

Автоматическая проверка **каждого** изменения кода сразу после его появления.

Проблема, которую решает: разработчик уверен, что изменение безобидное, и не проверяет. Ошибка попадает в основную ветку и обнаруживается через неделю, когда поверх неё написано много другого кода. Разбирать сложно и дорого.

Решение: проверка запускается автоматически, всегда, за минуты. Ошибка находится в момент внесения.

### Непрерывная доставка (CD)

Автоматическая упаковка проверенного кода в готовый к запуску артефакт и его доставка на сервер.

Проблема, которую решает: ручное развёртывание — это набор шагов, выполняемых человеком под давлением времени. Человек путает порядок, забывает шаг, копирует не тот файл.

Решение: последовательность описана кодом и выполняется одинаково каждый раз.

### Артефакт

Результат сборки. В нашем случае — образ контейнера.

Ключевое свойство: **неизменяемость**. Образ собирается один раз и дальше только копируется. Тестируется, публикуется и разворачивается один и тот же артефакт. Если бы на каждом этапе образ пересобирался заново, не было бы гарантии, что развёрнуто именно то, что проверено.

### Схема того, что будет построено

```
   Изменение кода
        │
        ├──► git push в ветку, запрос на слияние
        │         │
        │         ▼
        │    ┌──────────────────────────────────────┐
        │    │ ПРОВЕРКИ (часть IV)                  │
        │    │ линтеры → сборка → дымовой тест      │
        │    └──────────────────────────────────────┘
        │         │ только если всё зелёное
        │         ▼
        │    слияние в main разрешено
        │
        └──► git tag v1.0.0 + push тега
                  │
                  ▼
             ┌──────────────────────────────────────┐
             │ ВЫПУСК (часть V)                     │
             │ сборка образа → публикация в реестр  │
             │            ↓                         │
             │ проверка ОПУБЛИКОВАННОГО образа      │
             └──────────────────────────────────────┘
                  │ только если проверка прошла
                  ▼
             ┌──────────────────────────────────────┐
             │ РАЗВЁРТЫВАНИЕ (часть VI)             │
             │ SSH на сервер → получить образ →     │
             │ перезапустить → проверить ответ      │
             └──────────────────────────────────────┘
```

**Запомни главное разделение:**

| Событие | Что запускается | Почему так |
|---|---|---|
| Отправка кода в ветку | Только проверки | Быстро, безопасно, ничего никуда не уезжает |
| Создание тега | Выпуск и развёртывание | Тег — осознанное решение человека «эта версия идёт в работу» |

Если разворачивать на каждую отправку кода, любой случайный коммит уедет на боевой сервер. Тег ставит между разработкой и работой сервера явное решение человека.

## 8. Разберись в уровнях проверки

**Зачем этот раздел.** Слово «тестирование» покрывает разные вещи, работающие на разных уровнях. Не понимая уровней, ты либо проверяешь одно и то же трижды, либо оставляешь дыру.

### Уровни от дешёвых к дорогим

| № | Уровень | Что проверяет | Скорость | Где настроим |
|---|---|---|---|---|
| 1 | Статический анализ (линтеры) | Файлы, без запуска | Секунды | Часть IV |
| 2 | Модульные тесты | Отдельные функции кода | Секунды | Нет — тестировать нечего |
| 3 | Тест сборки | Собирается ли образ | Десятки секунд | Часть IV |
| 4 | Дымовой тест | Поднимается ли и отвечает ли приложение | Десятки секунд | Часть IV |
| 5 | Проверка артефакта | Работает ли **опубликованный** образ | Минута | Часть V |
| 6 | Проверка после развёртывания | Отвечает ли боевой сервер | Секунды | Часть VI |

**Порядок обязателен.** Дешёвые проверки идут первыми. Нет смысла тратить минуту на сборку образа, если линтер за две секунды нашёл опечатку.

### Почему уровня 2 у нас нет

Модульные тесты проверяют функции — блоки кода с логикой. В статической HTML-странице логики нет, проверять нечего. Уровень появится, когда в проекте появится JavaScript или серверная часть.

Это не пробел, а соответствие задаче. Добавлять пустые тесты ради галочки вредно: они создают ложное ощущение защищённости.

### Что такое дымовой тест

Минимальная проверка «включается ли вообще». Название пришло из электроники: собрал плату, подал питание — если дыма нет, можно проверять дальше.

Дымовой тест не проверяет, что приложение работает правильно. Он проверяет, что оно вообще запустилось. Это первая линия, отсекающая грубые поломки.

### Что такое линтер

Программа, читающая исходный текст и находящая проблемы **без выполнения**. Ловит опечатки, нарушения правил оформления, небезопасные конструкции.

Будем использовать три:
- `hadolint` — проверяет `Dockerfile`
- `actionlint` — проверяет файлы самой автоматизации
- `html-validate` — проверяет разметку страницы

# ЧАСТЬ III. ПЕРВАЯ АВТОМАТИЗАЦИЯ

Цель части: увидеть механику GitHub Actions на простейшем примере, прежде чем строить настоящий конвейер.

## 9. Выучи четыре понятия GitHub Actions

Без них дальше будет непонятно.

| Понятие | Что это |
|---|---|
| **Рабочий процесс** (workflow) | Файл `.yml` в папке `.github/workflows/`. Одна автоматизация. |
| **Событие** (блок `on:`) | Что запускает процесс: отправка кода, тег, запрос на слияние, нажатие кнопки. |
| **Задание** (job) | Отдельная одноразовая виртуальная машина. По умолчанию задания идут параллельно. |
| **Шаг** (step) | Одна команда (`run:`) или одно готовое действие (`uses:`) внутри задания. |

**Действие** (action) — переиспользуемый блок из чужого репозитория. Запись `actions/checkout@v6` означает: репозиторий `github.com/actions/checkout`, версия `v6`.

**Важно понимать про изоляцию.** Каждое задание получает чистую виртуальную машину. Файлы, созданные в одном задании, в другом отсутствуют. Даже код проекта там не появится сам — его нужно явно забрать шагом `actions/checkout`.

## 10. Запусти первый рабочий процесс

**Зачем этот шаг.** Он ничего полезного не делает. Его задача — показать механику: где лежит файл, как запускается, где смотреть результат. Разбираться с этим одновременно с настоящими проверками сложнее.

**Сделай:**

```bash
mkdir -p .github/workflows

cat > .github/workflows/hello.yml <<'EOF'
name: hello

# Два события: отправка кода в любую ветку и ручной запуск кнопкой
on:
  push:
  workflow_dispatch:

jobs:
  say-hello:
    runs-on: ubuntu-latest
    steps:
      - name: Поздороваться
        run: echo "Конвейер работает"

      - name: Показать, где мы находимся
        run: |
          echo "Ветка или тег: $GITHUB_REF"
          echo "Коммит: $GITHUB_SHA"
          echo "Операционная система:"
          uname -a
EOF
```

**Разбор:**
- `name:` — как процесс называется в интерфейсе.
- `runs-on: ubuntu-latest` — на какой машине выполнять. GitHub выдаёт чистую машину с Ubuntu, Docker и стандартными инструментами.
- `run: |` — вертикальная черта означает многострочную команду.
- `$GITHUB_REF`, `$GITHUB_SHA` — переменные окружения, которые GitHub подставляет сам.

**Отправь и посмотри:**

```bash
git add .github/workflows/hello.yml
git commit -m "ci: первый рабочий процесс"
git push
```

```bash
gh run watch
```

**Ожидаемый результат.** Команда покажет выполнение в реальном времени, затем — зелёную отметку об успехе.

**Посмотри журнал:**

```bash
gh run view --log
```

Найди в выводе свою строку «Конвейер работает».

**Запусти вручную:**

```bash
gh workflow run hello.yml
gh run watch
```

Это работает благодаря событию `workflow_dispatch`.

**Убери учебный файл:**

```bash
git rm .github/workflows/hello.yml
git commit -m "ci: убран учебный процесс"
git push
```

Механику увидел — дальше настоящие проверки.

## 11. Прогони линтеры на своей машине

**Зачем сначала локально.** Ключевой принцип: в конвейере запускается ровно та же команда, что у тебя. Тогда результат воспроизводим, и при сбое ты можешь повторить его локально, а не гадать по журналу.

Поэтому линтеры берутся контейнерами, а не готовыми действиями GitHub. Контейнер работает одинаково везде.

### Шаг 11.1. Проверь Dockerfile

**Сделай:**

```bash
docker run --rm -i hadolint/hadolint < Dockerfile
```

- `-i` — передать содержимое файла на вход контейнеру.
- `< Dockerfile` — перенаправление файла на вход.

**Ожидаемый результат.** Пустой вывод. Для линтеров пустой вывод означает «замечаний нет».

**Если появились замечания.** Каждое имеет код вида `DL3007`. Расшифровку легко найти по этому коду в документации hadolint.

### Шаг 11.2. Проверь файлы автоматизации

**Сделай:**

```bash
docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:latest -color
```

- `-v "$PWD:/repo"` — подключить текущую папку внутрь контейнера по пути `/repo`.
- `-w /repo` — сделать этот путь рабочим каталогом внутри контейнера.

**Ожидаемый результат.** Пустой вывод. Этот линтер ловит опечатки в названиях полей, несуществующие выражения, ошибки отступов — то есть ровно те проблемы, которые иначе обнаружились бы только после отправки кода.

### Шаг 11.3. Проверь разметку

**Сначала уточни, есть ли Node.js:**

```bash
node -v
```

Если команда не найдена, поставь:

```bash
sudo apt update && sudo apt install -y nodejs npm
```

**Задай правила проверки:**

```bash
cat > .htmlvalidate.json <<'EOF'
{
  "extends": ["html-validate:recommended"]
}
EOF
```

**Сделай:**

```bash
npx --yes html-validate index.html
```

- `npx` — запустить пакет без установки в систему.
- `--yes` — не спрашивать подтверждение на скачивание.

**Ожидаемый результат.** Сообщение о том, что проблем не найдено.

### Шаг 11.4. Проверь саму проверку

**Зачем.** Молчащий линтер и линтер, который ничего не проверяет, выглядят одинаково. Убедись, что он способен что-то поймать.

**Сделай:**

```bash
sed -i 's/<html lang="ru">/<html>/' index.html
npx --yes html-validate index.html
```

**Ожидаемый результат.** Линтер жалуется на отсутствие атрибута языка.

**Верни как было:**

```bash
sed -i 's/<html>/<html lang="ru">/' index.html
npx --yes html-validate index.html
```

## 12. Настрой автоматические проверки

**Что это.** Рабочий процесс с двумя заданиями: линтеры и сборка с дымовым тестом.

**Сделай:**

```bash
cat > .github/workflows/ci.yml <<'EOF'
name: ci

# События: отправка в main и любой запрос на слияние в main
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

# Права встроенного токена. Минимально необходимые.
permissions:
  contents: read

# Если пришло новое изменение, пока предыдущая проверка ещё идёт,
# старую отменить и не тратить ресурсы
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  lint:
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - name: Забрать код репозитория
        uses: actions/checkout@v6

      - name: Проверить Dockerfile
        run: docker run --rm -i hadolint/hadolint < Dockerfile

      - name: Проверить файлы автоматизации
        run: docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:latest -color

      - name: Проверить разметку
        run: npx --yes html-validate index.html

  smoke:
    runs-on: ubuntu-latest
    needs: lint            # запустится только после успешного задания lint
    timeout-minutes: 10
    steps:
      - name: Забрать код репозитория
        uses: actions/checkout@v6

      - name: Собрать образ
        run: docker build -t git-navigator:test .

      - name: Запустить контейнер
        run: docker run -d --name smoke -p 8080:80 git-navigator:test

      - name: Дымовой тест
        run: |
          curl -fsS --retry 10 --retry-delay 1 --retry-connrefused \
            http://localhost:8080 -o page.html
          grep -q "<title>Git Navigator</title>" page.html
          echo "Страница отдана и содержит ожидаемый заголовок"

      - name: Убрать контейнер
        if: always()       # выполнится даже если предыдущий шаг упал
        run: docker rm -f smoke
EOF
```

**Разбор ключевых мест:**

**`permissions: contents: read`** — встроенный токен получает только право читать код. Принцип минимальных прав: если процесс скомпрометирован, ущерб ограничен тем, что ему разрешено.

**`concurrency`** — при быстрой серии отправок кода отменяет предыдущие запуски. Экономит ресурсы и не путает результатами устаревших проверок.

**`timeout-minutes`** — предохранитель. Зависшее задание иначе будет крутиться до предела в шесть часов.

**`needs: lint`** — задания выполняются последовательно. Дешёвая проверка перед дорогой, как в разделе 8.

**`--retry-connrefused` у curl** — контейнер поднимается не мгновенно. Без повторных попыток тест падает через раз без реальной причины. Это самая частая причина «мигающих» тестов, которые проходят то так, то эдак.

**`-fsS` у curl** — флаг `-f` возвращает ошибку при ответе сервера 4xx/5xx. Без него `curl` считает успехом даже страницу «404 не найдено», и тест пропустит поломку.

**`grep -q` с конкретным заголовком** — проверяется не просто «что-то отдалось», а что отдалась именно наша страница.

**`if: always()`** — уборка выполняется в любом случае. На одноразовой машине GitHub некритично, но привычка правильная: на собственном сервере сборки мусорные контейнеры накапливаются и забивают диск.

**Отправь и проверь:**

```bash
git add .github/workflows/ci.yml .htmlvalidate.json
git commit -m "ci: линтеры и дымовой тест"
git push
gh run watch
```

**Ожидаемый результат.** Оба задания зелёные, `lint` выполнился первым.

## 15. Разберись с версиями и тегами

**Что такое тег в Git.** Именованный указатель на конкретный коммит. В отличие от ветки, не двигается.

**Правило именования — семантическое версионирование:**

```
v 1 . 4 . 2
  │   │   └── патч: исправления, ничего не сломано
  │   └────── минорная: новая возможность, старое работает
  └────────── мажорная: сломана совместимость
```

**Два вида тегов:**

```bash
# Простой: только указатель на коммит
git tag v1.0.0

# Аннотированный: полноценный объект с автором, датой и сообщением
git tag -a v1.0.0 -m "Первый релиз"
```

Для версий используй только аннотированный. Через полгода будет видно, кто и когда выпустил версию.

**Критически важно про порядок.** Файл рабочего процесса должен уже находиться в коммите, на который указывает тег. Поставишь тег раньше, чем отправишь файл — тег уедет, а запускать будет нечего.

Правильный порядок всегда: сначала `git push` файла, потом `git tag`, потом `git push origin тег`.

## 16. Настрой сборку и публикацию образа

**Что такое реестр.** Хранилище образов. Используем встроенный в GitHub — `ghcr.io`. Отдельная регистрация не нужна, права выдаются тем же встроенным токеном.

**Сделай:**

```bash
cat > .github/workflows/release.yml <<'EOF'
name: release

# Событие: отправка тега, начинающегося с буквы v
on:
  push:
    tags:
      - 'v*'

permissions:
  contents: read       # читать код
  packages: write      # писать образы в реестр

# Выпуски не отменяем: каждый должен дойти до конца
concurrency:
  group: release
  cancel-in-progress: false

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    outputs:
      # Передаём вычисленный номер версии в следующие задания
      version: ${{ steps.meta.outputs.version }}
    steps:
      - name: Забрать код репозитория
        uses: actions/checkout@v6

      - name: Подготовить сборщик Buildx
        uses: docker/setup-buildx-action@v4

      - name: Войти в реестр ghcr.io
        uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Вычислить имя и метки образа
        id: meta
        uses: docker/metadata-action@v6
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}

      - name: Собрать и опубликовать образ
        uses: docker/build-push-action@v7
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
EOF
```

**Разбор ключевых мест:**

**`secrets.GITHUB_TOKEN`** — временный токен, который GitHub создаёт на время запуска и уничтожает после. В настройки его добавлять не нужно, он существует всегда. Права задаются блоком `permissions`.

**`outputs`** — способ передать значение из одного задания в другое. Задания изолированы, переменные между ними сами не переходят.

**`docker/metadata-action`** — вычисляет метки образа из имени тега. Из тега `v1.0.0` получится три метки: `1.0.0`, `1.0` и `latest`. Метку `latest` действие добавляет само, когда видит тег по правилам семантического версионирования.

**`cache-from` / `cache-to`** — слои сборки сохраняются в кеш GitHub. Повторные сборки идут в разы быстрее: неизменившиеся слои не пересобираются.

**Версии действий** указаны актуальные: `checkout@v6`, `login-action@v4`, `setup-buildx-action@v4`, `metadata-action@v6`, `build-push-action@v7`. Более старые работают на Node.js 20, который убирают с серверов сборки в сентябре 2026 года.

## 17. Добавь проверку опубликованного образа

**Зачем это отдельное задание.** Это уровень 5 из раздела 8, и без него в конвейере дыра.

Смотри внимательно: задание `smoke` из части IV собирает образ **у себя** и тестирует его. Задание `build-and-push` собирает образ **заново** и публикует. Это два разных результата сборки. Обычно они совпадают, но гарантии нет.

Проверять нужно ровно тот артефакт, который поедет на сервер. Не пересобранный, а скачанный из реестра.

**Сделай.** Добавь в конец `release.yml`:

```yaml
  verify:
    runs-on: ubuntu-latest
    needs: build-and-push
    timeout-minutes: 10
    permissions:
      packages: read
    steps:
      - name: Войти в реестр ghcr.io
        uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Получить опубликованный образ
        env:
          IMAGE: ghcr.io/${{ github.repository }}:${{ needs.build-and-push.outputs.version }}
        run: |
          docker pull "$IMAGE"
          echo "Проверяется образ: $IMAGE"

      - name: Запустить и проверить
        env:
          IMAGE: ghcr.io/${{ github.repository }}:${{ needs.build-and-push.outputs.version }}
        run: |
          docker run -d --name verify -p 8080:80 "$IMAGE"
          curl -fsS --retry 10 --retry-delay 1 --retry-connrefused \
            http://localhost:8080 -o page.html
          grep -q "<title>Git Navigator</title>" page.html
          echo "Опубликованный образ работоспособен"

      - name: Убрать контейнер
        if: always()
        run: docker rm -f verify
```

Обрати внимание: здесь **нет** шага `actions/checkout`. Код проекта не нужен — проверяется готовый артефакт, как если бы его проверял посторонний.

# ЧАСТЬ VI. РАЗВЁРТЫВАНИЕ НА СЕРВЕР

Цель части: по тегу новая версия автоматически уезжает на сервер.

## 20. Подготовь сервер

Предполагается сервер (VPS) с Ubuntu 24.04 и доступом по SSH от провайдера.

### Шаг 20.1. Создай рабочего пользователя

**Зачем.** Работать под `root` опасно: любая ошибка необратима, любой процесс получает полные права. Нужен отдельный пользователь, повышающий права через `sudo` только когда надо.

**Сделай:**

```bash
ssh root@АДРЕС_СЕРВЕРА

adduser deploy          # запросит пароль и необязательные данные
usermod -aG sudo deploy
```

**Проверь:**

```bash
su - deploy
sudo whoami
```

**Ожидаемый результат.** Последняя команда после ввода пароля печатает `root` — значит повышение прав работает.

### Шаг 20.2. Создай ключ доступа для себя

**Зачем.** Пароль подбирается перебором. Ключ длиной 256 бит — нет. Приватная часть остаётся у тебя, публичная кладётся на сервер.

**Где выполнять.** На локальной машине, **не на сервере**.

**Сделай:**

```bash
ssh-keygen -t ed25519 -f ~/.ssh/vps_admin -C "admin@git-navigator"
```

- `-t ed25519` — современный алгоритм на эллиптических кривых. Короче и быстрее устаревшего RSA при большей стойкости.
- `-f путь` — куда сохранить. Создастся два файла: `vps_admin` (приватный, никому) и `vps_admin.pub` (публичный).
- `-C текст` — комментарий, чтобы через год понимать, что это за ключ.

Парольную фразу задай — этот ключ твой личный.

**Скопируй публичную часть на сервер:**

```bash
ssh-copy-id -i ~/.ssh/vps_admin.pub deploy@АДРЕС_СЕРВЕРА
```

Пароль спросят последний раз.

**Настрой короткий вход:**

```bash
cat >> ~/.ssh/config <<'EOF'

Host my-vps
    HostName 203.0.113.10
    User deploy
    IdentityFile ~/.ssh/vps_admin
    IdentitiesOnly yes
EOF

chmod 600 ~/.ssh/config
```

- `IdentitiesOnly yes` — предлагать серверу только указанный ключ. Без этого клиент перебирает все ключи подряд и сервер может разорвать соединение, исчерпав лимит попыток.

**Проверь:**

```bash
ssh my-vps 'hostname'
```

**Ожидаемый результат.** Имя сервера, без запроса пароля.

### Шаг 20.3. Отключи вход по паролю

**Зачем.** Пока вход по паролю разрешён, сервер круглосуточно перебирают автоматические сканеры. Отключение убирает этот класс атак целиком.

**Критично.** Держи открытым **второй сеанс SSH**. Ошибёшься в настройках и закроешь единственное соединение — останется только консоль в панели провайдера.

**Сделай на сервере:**

```bash
sudo tee /etc/ssh/sshd_config.d/99-hardening.conf > /dev/null <<'EOF'
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
EOF
```

**Почему отдельный файл, а не правка основного.** Основной `sshd_config` в Ubuntu подключает каталог `sshd_config.d`. Отдельный файл переживает обновление пакета, и сразу видно, что менялось руками.

**Проверь синтаксис до применения:**

```bash
sudo sshd -t
```

**Ожидаемый результат.** Пустой вывод. Ошибка здесь означает, что применять нельзя.

**Примени:**

```bash
sudo systemctl reload ssh
```

**Проверь из нового окна:**

```bash
ssh my-vps 'echo вход по ключу работает'
ssh -o PreferredAuthentications=password deploy@АДРЕС_СЕРВЕРА
```

**Ожидаемый результат.** Первая команда проходит. Вторая отказывает.

### Шаг 20.4. Закрой лишние порты

**Зачем.** Открытым должно быть только то, что нужно. Всё остальное закрыто по умолчанию.

**Сделай:**

```bash
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw enable
sudo ufw status
```

**Порядок важен.** Правило для SSH добавляется **до** включения межсетевого экрана. Включишь сначала — потеряешь соединение.

**Ожидаемый результат.** Список из двух разрешающих правил.

### Шаг 20.5. Установи Docker на сервер

Те же команды, что в разделе 2:

```bash
curl -fsSL https://get.docker.com -o get-docker.sh
sudo sh get-docker.sh
sudo usermod -aG docker deploy
```

**Применяй новую группу перезаходом:**

```bash
exit
ssh my-vps
docker run --rm hello-world
```

**Ожидаемый результат.** Приветственный текст Docker без `sudo`.

### Шаг 20.6. Создай отдельный ключ для автоматики

**Зачем.** Личный административный ключ в настройки GitHub не кладут никогда. Для автоматики — отдельная пара. Скомпрометирована — отзывается одной строкой, личный доступ не затронут.

**Сделай на локальной машине:**

```bash
ssh-keygen -t ed25519 -f ~/.ssh/gh_deploy -C "github-actions@git-navigator" -N ""
```

- `-N ""` — пустая парольная фраза. Обязательно: автоматика не сможет её ввести.

**Добавь публичную часть на сервер:**

```bash
cat ~/.ssh/gh_deploy.pub | ssh my-vps 'cat >> ~/.ssh/authorized_keys'
```

**Проверь:**

```bash
ssh -i ~/.ssh/gh_deploy -o IdentitiesOnly=yes deploy@АДРЕС_СЕРВЕРА 'docker --version'
```

**Ожидаемый результат.** Версия Docker без запроса пароля.

## 21. Передай данные в секреты

**Что такое секрет.** Зашифрованное значение в настройках репозитория. Автоматика получает его при запуске, в журналах оно автоматически заменяется звёздочками.

**Что туда класть.** Всё, что нельзя увидеть посторонним: приватные ключи, пароли, адреса внутренних систем. В код такое не попадает никогда.

**Сделай из папки проекта:**

```bash
gh secret set VPS_HOST --body "203.0.113.10"
gh secret set VPS_USER --body "deploy"

# Приватный ключ читается из файла, а не набирается руками
gh secret set VPS_SSH_KEY < ~/.ssh/gh_deploy

# Отпечаток сервера
gh secret set VPS_KNOWN_HOSTS --body "$(ssh-keyscan -t ed25519 203.0.113.10 2>/dev/null)"
```

**Зачем `VPS_KNOWN_HOSTS`.** Без него пришлось бы отключать проверку отпечатка флагом `StrictHostKeyChecking=no`. Это открывает подмену сервера посредником: автоматика подключилась бы к чему угодно, назвавшемуся твоим адресом. Правильный путь — заранее сохранить настоящий отпечаток.

**Проверь:**

```bash
gh secret list
```

**Ожидаемый результат.** Четыре имени с датами создания. Значения не показываются никогда, включая тебе.

## 22. Настрой автоматическое развёртывание

**Сделай.** Добавь в конец `release.yml`:

```yaml
  deploy:
    runs-on: ubuntu-latest
    needs: [build-and-push, verify]   # только после успешной проверки образа
    timeout-minutes: 10
    environment: production           # позволяет включить подтверждение человеком
    steps:
      - name: Подготовить ключ и отпечаток сервера
        run: |
          mkdir -p ~/.ssh
          chmod 700 ~/.ssh
          echo "${{ secrets.VPS_SSH_KEY }}" > ~/.ssh/id_ed25519
          chmod 600 ~/.ssh/id_ed25519
          echo "${{ secrets.VPS_KNOWN_HOSTS }}" > ~/.ssh/known_hosts
          chmod 644 ~/.ssh/known_hosts

      - name: Развернуть новую версию
        env:
          VPS_HOST: ${{ secrets.VPS_HOST }}
          VPS_USER: ${{ secrets.VPS_USER }}
          IMAGE: ghcr.io/${{ github.repository }}:${{ needs.build-and-push.outputs.version }}
        run: |
          ssh -o IdentitiesOnly=yes "$VPS_USER@$VPS_HOST" "IMAGE='$IMAGE' bash -s" <<'REMOTE'
          set -euo pipefail
          echo "Разворачивается: $IMAGE"
          docker pull "$IMAGE"
          docker rm -f git-navigator 2>/dev/null || true
          docker run -d \
            --name git-navigator \
            --restart unless-stopped \
            -p 80:80 \
            "$IMAGE"
          docker image prune -f
          REMOTE

      - name: Проверить, что сайт отвечает
        env:
          VPS_HOST: ${{ secrets.VPS_HOST }}
        run: |
          curl -fsS --retry 10 --retry-delay 2 --retry-connrefused \
            "http://$VPS_HOST/" -o page.html
          grep -q "<title>Git Navigator</title>" page.html
          echo "Боевой сервер отдаёт новую версию"
```

**Разбор ключевых мест:**

**Секреты через `env`, а не прямо в команде.** Если подставлять `${{ secrets.X }}` в текст команды, значение попадает в строку скрипта, и посторонний текст внутри секрета может выполниться как код. Через `env` значение приходит переменной окружения. Это общепринятая практика.

**`needs.build-and-push.outputs.version`** — разворачивается конкретная версия, а не подвижная метка `latest`. Всегда известно точно, что именно работает на сервере. Без этого откат превращается в угадывание.

**`<<'REMOTE'` в одинарных кавычках** — содержимое блока передаётся на сервер как есть, без подстановки на машине сборки. Переменная `$IMAGE` раскроется уже на сервере, потому что передана через `IMAGE='...' bash -s`.

**`set -euo pipefail`** — скрипт на сервере останавливается на первой ошибке. Без этого неудачное скачивание образа не помешает продолжить и сломать работающий контейнер.

**`docker rm -f ... || true`** — при первом развёртывании контейнера с таким именем ещё нет. Без `|| true` шаг упал бы на пустом месте.

**`--restart unless-stopped`** — контейнер поднимется сам после перезагрузки сервера.

**`docker image prune -f`** — удаление старых неиспользуемых образов. Без этого диск сервера постепенно заполняется.

**`environment: production`** — именованное окружение. В настройках репозитория (**Settings** → **Environments**) ему можно назначить обязательное подтверждение человеком: конвейер дойдёт до развёртывания и остановится, ожидая нажатия кнопки. Для боевых систем это стандартная практика.

**Выпусти версию:**

```bash
git add .github/workflows/release.yml
git commit -m "cd: развёртывание на сервер по тегу"
git push

git tag -a v1.0.1 -m "Проверка автоматического развёртывания"
git push origin v1.0.1

gh run watch
```

**Ожидаемый результат.** Три задания подряд: `build-and-push` → `verify` → `deploy`. Затем открой `http://АДРЕС_СЕРВЕРА` — страница на месте.

## 24. Научись откатываться

**Зачем.** Автоматическое развёртывание ценно ровно настолько, насколько быстро можно вернуться назад. План отката продумывается заранее, а не в момент аварии.

### Быстрый откат руками — секунды

```bash
ssh my-vps

docker rm -f git-navigator
docker run -d --name git-navigator --restart unless-stopped -p 80:80 \
  ghcr.io/ТВОЙ_ЛОГИН/git-navigator:1.0.1
```

Откат возможен именно потому, что каждая версия опубликована под собственной неизменяемой меткой. Это главный практический аргумент против развёртывания метки `latest`: под ней в разное время лежит разное, и вернуться некуда.

### Правильный откат через конвейер — минуты

Исправь код и выпусти новый тег `v1.0.3`. Состояние сервера остаётся описанным в репозитории, история сохраняется.

**Правило:** ручной откат — чтобы прямо сейчас остановить проблему. Выпуск новой версии — чтобы закрыть её по-настоящему.

## 25. Освой диагностику

### Со стороны GitHub

```bash
gh run list --limit 5              # последние запуски
gh run watch                       # наблюдение за текущим
gh run view --log-failed           # журнал только упавших шагов
gh run rerun --failed              # перезапустить упавшие задания
gh secret list                     # какие секреты заданы
```

### Со стороны сервера

```bash
ssh my-vps

docker ps                                      # что сейчас работает
docker logs --tail 50 git-navigator            # последние строки журнала
docker inspect git-navigator | grep -i image   # какая версия запущена
docker images                                  # какие образы лежат локально
df -h                                          # свободное место
```

### Работа с тегами

```bash
git tag -l                         # список локальных тегов
git tag -d v1.0.0                  # удалить локально
git push origin --delete v1.0.0    # удалить на GitHub
```

**Уточни для себя.** Удаление тега не удаляет уже опубликованный образ. Образы удаляются отдельно, через страницу пакета.

## 26. Типовые ошибки

| Симптом | Причина | Что сделать |
|---|---|---|
| Тег отправлен, ничего не запустилось | Файла процесса нет в коммите, на который указывает тег | Сначала `git push` файла, потом тег |
| `denied: permission_denied` при публикации | Не задан `permissions: packages: write` | Добавить блок в файл процесса |
| `Host key verification failed` | Секрет `VPS_KNOWN_HOSTS` пустой или устарел | Перезаписать выводом `ssh-keyscan` |
| `Permission denied (publickey)` | Ключ передан не полностью либо публичная часть не добавлена на сервер | Перезаписать через `gh secret set VPS_SSH_KEY < файл` |
| Дымовой тест падает через раз | Контейнер не успевает подняться | Повторные попытки у `curl` |
| `port is already allocated` | Порт 80 занят другим сервисом | Остановить его или изменить проброс |
| Диск сервера заполняется | Копятся старые образы | `docker image prune -f` в скрипте развёртывания |
| Проверка не появляется в списке обязательных | Задание ни разу не выполнялось | Отправить код, затем настраивать защиту ветки |
| `npx: command not found` в WSL | Node.js не установлен | `sudo apt install -y nodejs npm` |

## 27. Словарь

| Понятие | Значение |
|---|---|
| **CI** | Непрерывная интеграция. Автоматическая проверка каждого изменения кода. |
| **CD** | Непрерывная доставка. Автоматическая упаковка и доставка проверенного кода. |
| **Конвейер** | Вся цепочка от изменения кода до работающего приложения. |
| **Артефакт** | Результат сборки. Здесь — образ контейнера. Неизменяем. |
| **Реестр** | Хранилище образов. Здесь — `ghcr.io`. |
| **Образ** | Шаблон, из которого создаются контейнеры. |
| **Контейнер** | Запущенный экземпляр образа. |
| **Линтер** | Программа проверки исходного текста без его выполнения. |
| **Дымовой тест** | Минимальная проверка базовой работоспособности. |
| **Рабочий процесс** | Файл `.yml` в `.github/workflows/`. Одна автоматизация. |
| **Задание** | Изолированная одноразовая виртуальная машина внутри процесса. |
| **Событие** | То, что запускает процесс: отправка кода, тег, запрос на слияние. |
| **Секрет** | Зашифрованное значение в настройках репозитория, скрытое в журналах. |
| **Семантическое версионирование** | Схема номеров версий `МАЖОРНАЯ.МИНОРНАЯ.ПАТЧ`. |
| **Откат** | Возврат на предыдущую работающую версию. |

## 28. Итоговое состояние проекта

```
git-navigator/
├── .github/
│   └── workflows/
│       ├── ci.yml              # проверки: линтеры + сборка + дымовой тест
│       └── release.yml         # выпуск: сборка → публикация → проверка → развёртывание
├── .dockerignore               # что не попадает в контекст сборки
├── .htmlvalidate.json          # правила проверки разметки
├── Dockerfile                  # описание образа
├── index.html                  # содержимое страницы
└── SETUP_GUIDE.md              # это руководство
```

### Ежедневный цикл работы

```bash
# 1. Начни изменение в отдельной ветке
git switch -c feature/новый-текст
nano index.html

# 2. Проверь локально до отправки
docker run --rm -i hadolint/hadolint < Dockerfile
npx --yes html-validate index.html

# 3. Отправь
git add . && git commit -m "feat: обновлён текст страницы"
git push -u origin feature/новый-текст

# 4. Открой запрос на слияние, дождись проверок
gh pr create --fill
gh pr checks --watch

# 5. Влей
gh pr merge --squash --delete-branch

# 6. Выпусти версию
git switch main && git pull
git tag -a v1.0.3 -m "Обновление текста"
git push origin v1.0.3
gh run watch
```

## 29. Куда двигаться дальше

По возрастанию сложности:

1. **Сертификат HTTPS.** Обратный прокси-сервер Caddy получает и продлевает сертификаты сам, настройка занимает несколько строк.
2. **Развёртывание без простоя.** Сейчас между остановкой старого контейнера и запуском нового проходит секунда-две недоступности. Решается запуском нового контейнера рядом и переключением прокси.
3. **Файл `docker-compose.yml` на сервере.** Понадобится, когда сервисов станет больше одного.
4. **Проверка образа на уязвимости.** Trivy отдельным заданием между публикацией и развёртыванием.
5. **Закрепление действий по контрольной сумме коммита** вместо мажорной версии. Защита от подмены содержимого стороннего действия.
6. **Автоматическое обновление зависимостей.** Dependabot следит за выходом новых версий действий и открывает запросы на слияние сам.
7. **Модульные тесты.** Появятся вместе с первым кодом, содержащим логику. Тогда же появится уровень 2 из раздела 8.
8. **Защита сервера от перебора.** Fail2ban блокирует адреса после серии неудачных попыток входа.
