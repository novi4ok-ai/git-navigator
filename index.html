1. Конфигурация Git

Более специфичный уровень перекрывает менее специфичный. Для личной/корпоративной идентичности это ключевое правило.

Имя автора глобально

Задаёт имя автора по умолчанию для всех ваших репозиториев. Это имя будет записываться в каждый новый commit, если внутри конкретного проекта не задано другое значение.

git config --global user.name "Ваше Имя"

Email глобально

Задаёт email автора по умолчанию для всех репозиториев текущего пользователя. Именно этот адрес будет попадать в новые commits и часто используется GitHub/GitLab для привязки commit к аккаунту.

git config --global user.email "you@example.com"

Email только для проекта

Задаёт email только для текущего репозитория. Такая local-настройка перекрывает global и удобна, когда личные проекты нужно подписывать личной почтой, а рабочие — корпоративной.

git config --local user.email "you@company.example"

Новые репозитории с main

Устанавливает имя начальной ветки для будущих репозиториев, созданных через git init. Уже существующие репозитории и ветки эта настройка не переименовывает.

git config --global init.defaultBranch main

Редактор Git

Указывает, какой текстовый редактор Git должен открывать для commit message, interactive rebase и других операций. В примере используется VS Code, который ждёт закрытия открытого файла.

git config --global core.editor "code --wait"

Pull через rebase

Делает rebase поведением git pull по умолчанию. Вместо автоматического merge Git обычно переносит ваши локальные commits поверх полученных изменений, сохраняя историю более линейной.

git config --global pull.rebase true

Автоочистка remote refs

Включает автоматическую очистку устаревших remote-tracking ссылок при fetch. Если ветку удалили на сервере, после fetch её старая ссылка вроде origin/feature больше не будет висеть локально.

git config --global fetch.prune true

Показать источник настроек

Показывает все итоговые настройки Git, их область действия и файл, из которого каждая настройка была прочитана. Особенно полезно при поиске конфликтов между system, global и local config.

git config --show-origin --show-scope --list

Проверить одну настройку

Показывает итоговое значение одной настройки и источник, откуда оно было взято. Удобно проверить, какой именно email, editor или другой параметр реально действует в текущем репозитории.

git config --show-origin --show-scope --get user.email

Одноразовое значение

Применяет настройку только к одной выполняемой команде и ничего не записывает в конфигурационные файлы. После завершения команды обычные настройки Git снова действуют как раньше.

git -c user.email="temp@example.com" commit -m "message"

Приоритет конфигурации

system → global → local → worktree → command
Практика: личные значения — global; корпоративные — local или includeIf.

Автоматический корпоративный профиль через includeIf

В ~/.gitconfig:

[user] name = Alexander email = personal@example.com [includeIf "gitdir:~/Projects/customer/"] path = ~/.gitconfig-customer

В ~/.gitconfig-customer:

[user] name = Alexander email = alexander@company.example

Переносы строк: Windows / Linux

Windows: core.autocrlf

На Windows преобразует LF в CRLF при checkout и обратно в LF при commit для текстовых файлов. Используйте осознанно и лучше вместе с .gitattributes, чтобы правила окончания строк были едиными для команды.

git config --global core.autocrlf true

Linux/macOS: core.autocrlf

На Linux/macOS сохраняет LF в рабочем каталоге, но при добавлении в Git может нормализовать CRLF в LF. Это распространённый вариант для Unix-подобных систем.

git config --global core.autocrlf input
Для командной разработки: правила EOL лучше фиксировать в .gitattributes внутри репозитория — это воспроизводимо для всех участников.

Создать репозиторий

Создаёт новый Git-репозиторий в текущем каталоге, добавляя служебную папку .git. Существующие файлы не коммитятся автоматически — их ещё нужно добавить через git add и зафиксировать.

git init

Клонировать репозиторий

Создаёт локальную копию удалённого репозитория вместе с его ветками и историей commits. Обычно после clone remote с именем origin настраивается автоматически.

git clone https://github.com/user/repo.git

Клонировать в свой каталог

Клонирует удалённый репозиторий, но сохраняет его в каталог с указанным вами именем. Полезно, когда локальная папка должна называться иначе, чем репозиторий на сервере.

git clone https://github.com/user/repo.git my-project

2. Основной рабочий цикл

Состояние репозитория

Показывает текущее состояние рабочей копии: изменённые, новые, удалённые и уже подготовленные к commit файлы. Это безопасная команда, которую полезно выполнять перед add, commit, pull и reset.

git status

Краткий status

Выводит тот же статус в компактном формате и дополнительно показывает текущую ветку и её связь с upstream. Удобно для быстрой проверки состояния проекта перед работой.

git status -sb

Добавить файл

Добавляет указанный файл в staging area — набор изменений, который попадёт в следующий commit. Сам файл при этом не коммитится: commit выполняется отдельной командой.

git add path/to/file

Добавить всё

Добавляет в staging все изменения в репозитории: новые файлы, изменения существующих и удаления. Перед commit полезно проверить результат через git diff --staged.

git add -A

Commit

Создаёт новый commit из файлов и изменений, которые уже находятся в staging area. Текст после -m — краткое описание того, что было изменено и зачем.

git commit -m "Краткое описание"

Изменить последний commit осторожно

Пересоздаёт последний commit: можно изменить его сообщение и/или добавить в него новые staged-изменения. Если commit уже опубликован, его переписывание потребует особой осторожности.

git commit --amend
Важно: amend переписывает последний commit.

Push

Отправляет локальные commits текущей ветки в связанную удалённую upstream-ветку. Если upstream ещё не настроен, Git попросит указать, куда именно отправлять ветку.

git push

Pull через rebase

Сначала получает свежие изменения из удалённой ветки, затем переносит ваши локальные commits поверх них. Это помогает избежать лишнего merge-commit при обычной синхронизации.

git pull --rebase

3. Ветки

Текущая ветка

Показывает только имя ветки, на которой вы сейчас находитесь. Удобно в терминале, скриптах и перед командами, которые зависят от текущей ветки.

git branch --show-current

Локальные ветки

Показывает список локальных веток репозитория. Текущая ветка отмечается символом *, поэтому сразу видно, где вы сейчас работаете.

git branch

Все ветки

Показывает локальные ветки и remote-tracking ветки вроде origin/main. Полезно после git fetch, чтобы увидеть ветки, существующие на удалённом сервере.

git branch -a

Tracking / upstream

Показывает локальные ветки вместе с их upstream и последним commit. По этому выводу удобно понять, какая ветка связана с origin и есть ли расхождение по commits.

git branch -vv

Создать и переключиться

Создаёт новую ветку от текущего commit и сразу переключает рабочую копию на неё. Это стандартный способ начать отдельную feature, fix или experiment ветку.

git switch -c feature/login

Переключиться

Переключает рабочую копию на уже существующую ветку. Git обновит файлы так, чтобы они соответствовали состоянию выбранной ветки.

git switch main

Переименовать текущую

Переименовывает текущую локальную ветку. Например, находясь на master, этой командой можно изменить её имя на main.

git branch -m main

Переименовать другую

Переименовывает указанную локальную ветку без необходимости сначала на неё переключаться. Первый аргумент — старое имя, второй — новое.

git branch -m old-name new-name

Слитые ветки

Показывает локальные ветки, commits которых уже вошли в текущую ветку. Обычно используется перед безопасным удалением старых feature-веток.

git branch --merged

Удалить ветку

Удаляет локальную ветку только если Git считает её изменения уже слитыми. Это предпочтительный и более безопасный вариант обычного удаления веток.

git branch -d feature/login

Удалить принудительно опасно

Принудительно удаляет локальную ветку, даже если в ней есть неслитые commits. Используйте только когда точно уверены, что эти commits больше не нужны.

git branch -D feature/login

Переименовать уже опубликованную ветку

  1. Переименовать локально:
    git branch -m old-name new-name
  2. Опубликовать новое имя и назначить upstream:
    git push -u origin new-name
  3. Удалить старое имя на сервере:
    git push origin --delete old-name

4. Remote: origin, upstream, fetch, push

origin — стандартное имя основного remote. В fork-сценарии исходный проект часто называют upstream.

Список remote

Показывает все настроенные удалённые репозитории и URL, используемые для fetch и push. Обычно основной remote называется origin.

git remote -v

Подробности origin

Показывает подробную информацию об origin: URL, remote HEAD, отслеживаемые ветки и настройки push/pull. Полезно для диагностики связи локального проекта с сервером.

git remote show origin

Добавить origin

Добавляет удалённый репозиторий под именем origin. После этого можно выполнять fetch, pull и push, не вводя полный URL каждый раз.

git remote add origin https://github.com/user/repo.git

Изменить URL

Меняет URL уже существующего remote. Частый сценарий — переключить origin с HTTPS на SSH или перенести проект на другой сервер.

git remote set-url origin git@github.com:user/repo.git

Переименовать remote

Переименовывает только локальное имя remote. Сам удалённый репозиторий и его адрес при этом не изменяются.

git remote rename origin upstream

Удалить remote

Удаляет remote из локальной конфигурации репозитория. Это не удаляет сам проект на GitHub/GitLab и не стирает его данные на сервере.

git remote remove origin

Fetch

Получает свежие commits, ветки и ссылки с origin, но не меняет текущую ветку и рабочие файлы. Безопасный способ сначала посмотреть, что изменилось на сервере.

git fetch origin

Fetch + prune

Выполняет fetch и одновременно удаляет локальные remote-tracking ссылки на ветки, которые уже удалены на сервере. Локальные обычные ветки не удаляются.

git fetch --prune

Первый push ветки

Публикует локальную ветку на origin и одновременно назначает её upstream. После этого для этой ветки обычно достаточно обычных git push и git pull.

git push -u origin feature/login

Удалить remote-ветку

Удаляет указанную ветку на удалённом репозитории origin. Локальная ветка при этом остаётся и при необходимости удаляется отдельно.

git push origin --delete feature/login

Fork → upstream → синхронизация

  1. Проверить remotes:
    git remote -v
  2. Добавить исходный проект:
    git remote add upstream https://github.com/original/project.git
  3. Получить изменения:
    git fetch upstream
  4. Обновить main:
    git switch main git rebase upstream/main
  5. Обновить свой fork:
    git push origin main

5. Просмотр изменений — diff

Рабочая копия vs staging

Показывает изменения в рабочих файлах, которые ещё не были добавлены в staging через git add. Ничего не изменяет и безопасен для просмотра.

git diff

Staged vs HEAD

Показывает изменения, уже добавленные в staging area и готовые попасть в следующий commit. Это хороший финальный контроль перед git commit.

git diff --staged

Две ветки

Сравнивает содержимое двух веток и показывает различия между их состояниями. Полезно перед merge или code review, чтобы понять объём изменений.

git diff main..feature/login

Два commit

Сравнивает два произвольных commits по их HASH и показывает, что изменилось между ними. Подходит для анализа конкретного участка истории.

git diff HASH1 HASH2

Статистика

Показывает компактную статистику изменений: какие файлы затронуты и сколько строк добавлено или удалено. Удобно, когда полный diff слишком большой.

git diff --stat

Только имена

Показывает только имена изменённых файлов без содержимого изменений. Полезно для быстрой проверки и автоматизации в shell-скриптах.

git diff --name-only

6. История и поиск

История

Показывает историю commits текущей ветки с автором, датой, HASH и сообщением. Выход можно прокручивать и фильтровать дополнительными параметрами.

git log

Компактный граф

Показывает компактную историю всех веток в виде текстового графа. Удобно видеть ответвления, merge, теги и положение HEAD в одном представлении.

git log --oneline --graph --decorate --all

Один commit

Показывает подробности одного объекта commit: автора, сообщение и сделанные изменения. Вместо полного HASH обычно достаточно его уникального короткого начала.

git show <commit>

По автору

Фильтрует историю и показывает только commits указанного автора. Поиск учитывает имя и email, записанные в данных commit.

git log --author="Alexander"

По времени

Ограничивает историю указанным периодом времени. В примере будут показаны commits не старше двух недель от текущего момента.

git log --since="2 weeks ago"

По commit message

Ищет текст в сообщениях commits. Полезно, если вы помните слова из описания исправления, но не знаете HASH нужного commit.

git log --grep="fix login"

Когда менялась строка

Ищет commits, в которых изменилось количество указанной строки или фрагмента текста. Особенно полезно для поиска момента, когда код или настройка появились либо исчезли.

git log -S"searchText"

История файла + patch

Показывает историю только выбранного файла и сразу выводит patch каждого изменения. Так проще проследить, как конкретный файл менялся со временем.

git log -p -- path/to/file

Поиск в tracked-файлах

Ищет текст внутри файлов, которые Git отслеживает в текущем репозитории. Работает похоже на grep, но знает структуру Git-проекта.

git grep "searchText"

Кто менял строки

Для каждой строки файла показывает commit и автора, который последним её изменял. Полезно при расследовании происхождения конкретного участка кода.

git blame path/to/file

7. Merge и конфликты

Влить ветку

Вливает указанную ветку в текущую ветку. Если изменения совместимы, Git выполнит merge автоматически; при пересечении изменений может потребоваться разрешить конфликты.

git merge feature/login

Конфликтующие файлы

Показывает только файлы, которые сейчас находятся в состоянии merge-конфликта. Это удобный список того, что нужно исправить вручную.

git diff --name-only --diff-filter=U

Отметить решённым

После ручного исправления конфликтующего файла добавляет его в staging и тем самым сообщает Git, что конфликт в этом файле разрешён.

git add path/to/file

Завершить merge

После разрешения всех конфликтов создаёт commit, завершающий merge. Git обычно сам предложит подходящее сообщение merge-commit.

git commit

Отменить merge

Отменяет незавершённый merge и пытается вернуть рабочую копию к состоянию до его начала. Используйте, если решили не продолжать конфликтное слияние.

git merge --abort

Взять ours осторожно

Для конфликтующего файла выбирает версию с нашей стороны текущей операции. Перед использованием обязательно проверьте контекст merge/rebase, чтобы не выбрать не ту версию.

git restore --ours path/to/file

Взять theirs осторожно

Для конфликтующего файла выбирает версию с другой стороны текущей операции. Значение theirs зависит от контекста, поэтому результат нужно проверить перед commit.

git restore --theirs path/to/file

Как выглядит конфликт

<<<<<<< HEAD ваша версия ======= версия из другой ветки >>>>>>> feature/login
Что делать: оставить правильный итоговый текст, удалить маркеры конфликта, затем выполнить git add.
ours / theirs: при rebase смысл сторон может быть неинтуитивным. Перед автоматическим выбором стороны проверьте содержимое файла.

8. Rebase и безопасный force push

Rebase на main переписывает историю

Переносит commits текущей ветки поверх актуального состояния main, создавая для них новые HASH. Удобно для линейной истории, но опубликованную историю переписывать нужно осторожно.

git rebase main

Interactive rebase

Открывает интерактивный список последних пяти commits, где их можно переименовать, объединить, переставить или удалить. Это мощный инструмент для подготовки аккуратной истории перед публикацией.

git rebase -i HEAD~5

Продолжить

Продолжает остановленный rebase после того, как вы исправили конфликты и добавили исправленные файлы через git add. Git перейдёт к следующему commit.

git rebase --continue

Пропустить commit осторожно

Пропускает текущий commit во время rebase и не применяет его изменения. Используйте только если понимаете, что этот commit действительно должен исчезнуть из итоговой истории.

git rebase --skip

Отменить rebase

Полностью отменяет текущий незавершённый rebase и возвращает ветку к состоянию до его запуска. Это безопасный способ отказаться от неудачного rebase.

git rebase --abort

Безопаснее force предпочтительно

Принудительно обновляет удалённую ветку, но сначала проверяет, что она не изменилась неожиданно с момента вашего последнего fetch. Это предпочтительнее обычного --force после rebase.

git push --force-with-lease

Обычный force опасно

Безусловно переписывает удалённую ветку вашим локальным состоянием. Может уничтожить чужие новые commits, поэтому обычно вместо него следует использовать --force-with-lease.

git push --force

Команды interactive rebase

КомандаЧто делает
pickОставить commit.
rewordИзменить commit message.
squashОбъединить с предыдущим и отредактировать сообщение.
fixupОбъединить с предыдущим без отдельного сообщения.
dropУдалить commit из переписываемой истории.
Почему --force-with-lease лучше: он проверяет ожидаемое состояние remote-ветки и снижает риск затереть чужие новые commits. Это не делает force push полностью безопасным.

9. Как отменять ошибки

СитуацияКомандаРезультат
Случайно сделал git addgit restore --staged fileУбирает из staging, рабочие изменения остаются.
Хочу выбросить изменения файлаgit restore fileУдаляет незакоммиченные tracked-изменения.
Ошибка в последнем commit messagegit commit --amendПересоздаёт последний commit.
Отменить опубликованный commitgit revert HASHСоздаёт новый обратный commit, не переписывая опубликованную историю.
Отменить последний локальный commitgit reset --mixed HEAD~1Commit исчезает, изменения остаются unstaged.
Отменить commit, оставить staginggit reset --soft HEAD~1Commit исчезает, изменения остаются staged.
Потерял commit после reset/rebasegit reflogПозволяет найти прежнее положение HEAD.

Жёсткий reset опасно

Перемещает текущую ветку на выбранный commit и приводит staging и рабочие tracked-файлы к его состоянию. Незакоммиченные tracked-изменения будут потеряны, поэтому команда опасна.

git reset --hard <commit>
Потеря данных: незакоммиченные tracked-изменения удаляются.

Dry-run clean

Показывает, какие untracked-файлы и каталоги были бы удалены командой git clean, но ничего не удаляет. Всегда полезно запускать этот dry-run первым.

git clean -nd

Удалить untracked опасно

Удаляет untracked-файлы и каталоги из рабочей копии. Эти данные могут не находиться в Git вообще, поэтому перед выполнением обязательно проверьте git clean -nd.

git clean -fd

10. Reflog и восстановление

Reflog

Показывает локальный журнал перемещений HEAD и других refs: checkout, reset, rebase, commit и другие операции. Часто помогает найти commit, который кажется потерянным.

git reflog

Проверить найденный commit

Показывает содержимое найденного commit перед восстановлением. Так можно убедиться, что HASH из reflog действительно указывает на нужную версию проекта.

git show <HASH>

Спасательная ветка

Создаёт новую ветку recovery на найденном commit и переключается на неё. Это безопасный способ сначала сохранить потерянную точку истории отдельной ссылкой.

git switch -c recovery <HASH>

Спасательный сценарий после ошибочного reset/rebase

  1. Найти старый HEAD:
    git reflog
  2. Проверить commit:
    git show HASH
  3. Создать спасательную ветку:
    git switch -c recovery HASH

11. Stash — временно убрать работу

Спрятать tracked

Временно сохраняет незакоммиченные изменения отслеживаемых файлов в stash и очищает рабочую копию. Полезно, когда нужно быстро переключиться на другую задачу.

git stash push -m "WIP"

Включая untracked

Сохраняет в stash не только изменения tracked-файлов, но и новые untracked-файлы. Игнорируемые через .gitignore файлы по умолчанию сюда всё равно не входят.

git stash push -u -m "WIP"

Список stash

Показывает список всех сохранённых stash-записей с номерами вроде stash@{0}. Самая новая запись обычно находится под номером 0.

git stash list

Посмотреть patch

Показывает полный diff выбранного stash. Полезно проверить его содержимое перед apply, pop или удалением.

git stash show -p stash@{0}

Apply

Применяет изменения выбранного stash к текущей рабочей копии, но оставляет сам stash в списке. Это удобно, если резервную копию изменений пока хочется сохранить.

git stash apply stash@{0}

Pop

Применяет последний stash и, если применение прошло успешно, удаляет эту запись из stash-списка. При конфликтах запись обычно сохраняется.

git stash pop

Отдельная ветка

Создаёт новую ветку от того commit, на котором был создан stash, и пытается применить stash туда. Полезно, если текущая ветка сильно изменилась и обычный pop конфликтует.

git stash branch rescue stash@{0}

Удалить запись

Удаляет выбранную stash-запись без применения её изменений. Перед удалением полезно проверить содержимое через git stash show -p.

git stash drop stash@{0}

Очистить всё опасно

Удаляет все сохранённые stash-записи сразу. Восстановление после этого может быть затруднено, поэтому используйте только если уверены, что они больше не нужны.

git stash clear

12. .gitignore

Каталог

Правило с завершающим / игнорирует каталог node_modules и всё его содержимое. Такой шаблон часто используют для зависимостей, которые можно восстановить из package manager.

node_modules/

Файл

Игнорирует конкретный файл .env. Это типичный способ не отправлять в репозиторий локальные переменные окружения и секреты.

.env

Расширение

Игнорирует все файлы с расширением .log в областях, где действует этот .gitignore. Подходит для журналов, которые генерируются программой и не должны версионироваться.

*.log

Только от корня .gitignore

Начальный / привязывает правило к каталогу, где расположен этот .gitignore. Поэтому будет игнорироваться именно build в этом месте, а не любой build глубже по дереву.

/build/

На любом уровне

Шаблон ** позволяет совпадению проходить через несколько уровней каталогов. В этом примере любой каталог tmp ниже текущей области .gitignore будет игнорироваться.

**/tmp/

Исключение

Сначала игнорирует все файлы, начинающиеся с .env, а затем правилом ! возвращает .env.example в отслеживаемые. Так удобно хранить шаблон настроек без реальных секретов.

.env* !.env.example

Один символ

Символ ? соответствует ровно одному произвольному символу в имени. Например правило совпадёт с file1.txt и fileA.txt, но не с file10.txt.

file?.txt

Диапазон

Квадратные скобки задают один символ из диапазона или набора. Здесь будут совпадать file0.log, file1.log … file9.log.

file[0-9].log

Основные правила .gitignore

  1. # — комментарий; для буквального # в начале используйте \#.
  2. * — любое количество символов, но не разделитель каталогов.
  3. ? — один символ, кроме разделителя каталогов.
  4. ** — шаблон через несколько уровней.
  5. dir/ — каталог.
  6. /dir/ — путь относительно расположения данного .gitignore.
  7. !pattern — повторное включение, если Git может обойти родительский путь.

Практический шаблон

# Секреты .env .env.* !.env.example *.key *.pem # Логи *.log logs/ # Временное tmp/ temp/ *.tmp # Зависимости node_modules/ .venv/ __pycache__/ # Сборка /build/ /dist/ # ОС .DS_Store Thumbs.db

Почему игнорируется?

Показывает, почему конкретный путь игнорируется: файл с правилом, номер строки и сам шаблон. Это основная команда для диагностики неожиданного поведения .gitignore.

git check-ignore -v path/to/file

Показать ignored

Добавляет игнорируемые файлы и каталоги в вывод git status. Удобно проверить, что правила .gitignore работают так, как вы ожидаете.

git status --ignored

Уже tracked-файл

Убирает уже отслеживаемый файл из Git index, но оставляет его на диске. После этого правило .gitignore сможет скрывать его от последующего добавления.

git rm --cached path/to/file

Уже tracked-каталог

Рекурсивно убирает уже отслеживаемый каталог из Git index, сохраняя локальные файлы. Обычно после этого изменение нужно зафиксировать отдельным commit.

git rm -r --cached path/to/directory/

Только локально

Файл .git/info/exclude содержит ignore-правила только для вашей локальной копии репозитория. Он не коммитится и поэтому не влияет на других разработчиков.

.git/info/exclude

Глобальный ignore

Указывает глобальный файл ignore для текущего пользователя. Туда удобно поместить системные или редакторские файлы, которые не относятся к конкретному проекту.

git config --global core.excludesFile ~/.gitignore_global
Если секрет уже попал в опубликованную историю: .gitignore его не удаляет. Секрет нужно отозвать/заменить; очистка истории — отдельная операция.

13. .gitattributes — EOL и типы файлов

Практический .gitattributes

* text=auto *.sh text eol=lf *.py text eol=lf *.bat text eol=crlf *.cmd text eol=crlf *.png binary *.jpg binary *.zip binary
Зачем: фиксирует единые правила EOL и обработки файлов для всей команды.

Проверить атрибуты

Показывает все Git-атрибуты, которые реально применяются к указанному файлу. Полезно при диагностике правил eol, text, binary и других записей из .gitattributes.

git check-attr -a -- path/to/file

Перенормализовать проверьте diff

Повторно применяет правила нормализации из .gitattributes ко всем tracked-файлам и добавляет получившиеся изменения в staging. После выполнения обязательно проверьте diff перед commit.

git add --renormalize .

14. Теги и релизы

Список тегов

Показывает список локальных тегов репозитория. Теги обычно используют как постоянные имена для важных commits, например релизов v1.0.0.

git tag

Annotated tag

Создаёт аннотированный тег с отдельным объектом, автором, датой и сообщением. Такой тип обычно предпочтителен для официальных релизов.

git tag -a v1.2.0 -m "Release v1.2.0"

Lightweight tag

Создаёт lightweight-тег — простую именованную ссылку на текущий commit без отдельного сообщения и объекта tag. Подходит для временных или простых меток.

git tag v1.2.0

Показать тег

Показывает информацию о теге и объекте, на который он указывает. Для annotated tag также видны данные tagger и сообщение тега.

git show v1.2.0

Push одного тега

Отправляет на origin один конкретный тег. Обычный git push ветки не гарантирует публикацию всех локальных тегов.

git push origin v1.2.0

Push всех тегов

Отправляет на удалённый репозиторий все локальные теги, которых там ещё нет. Перед этим полезно убедиться, что среди них нет временных меток.

git push --tags

Удалить локально

Удаляет указанный тег только из локального репозитория. Если тег уже опубликован, удалять его на сервере нужно отдельной командой.

git tag -d v1.2.0

Удалить на origin

Удаляет тег из удалённого репозитория origin через явное удаление ref. Локальный тег при этом остаётся, если его не удалить отдельно.

git push origin :refs/tags/v1.2.0

15. GitHub / GitLab через SSH

Создать ED25519-ключ

Создаёт пару SSH-ключей современного типа ED25519: приватный и публичный. Приватный ключ остаётся у вас, а содержимое файла .pub добавляется в GitHub/GitLab.

ssh-keygen -t ed25519 -C "you@example.com"

Публичный ключ

Показывает публичную часть SSH-ключа, которую можно безопасно скопировать в настройки GitHub или GitLab. Приватный файл без .pub никому передавать нельзя.

cat ~/.ssh/id_ed25519.pub

Проверить GitHub

Проверяет SSH-аутентификацию на GitHub без клонирования или push. При первом подключении SSH может отдельно спросить подтверждение fingerprint сервера.

ssh -T git@github.com

Проверить GitLab.com

Проверяет SSH-аутентификацию на GitLab.com. Команда помогает убедиться, что ключ добавлен в аккаунт и SSH использует правильную пару ключей.

ssh -T git@gitlab.com

Переключить origin на SSH

Меняет URL origin с текущего адреса на SSH-формат GitHub. После этого fetch, pull и push для этого remote будут использовать SSH-аутентификацию.

git remote set-url origin git@github.com:user/repo.git
HTTPS vs SSH: оба способа нормальны. SSH удобен для постоянной разработки; HTTPS обычно используют вместе с credential manager или токенами.

16. Полезные aliases

Короткий status

Создаёт глобальный псевдоним git st для короткого git status -sb. Alias экономит ввод, но выполняет ту же самую Git-команду с указанными параметрами.

git config --global alias.st "status -sb"

Красивый log

Создаёт псевдоним git lg для компактного графа истории всех веток. После настройки длинную команду log можно вызывать двумя буквами.

git config --global alias.lg "log --oneline --graph --decorate --all"

Последний commit

Создаёт псевдоним git last, который показывает последний commit вместе со статистикой изменённых файлов. Удобно быстро проверить, что было зафиксировано последним.

git config --global alias.last "log -1 HEAD --stat"

Использование

git st git lg git last

17. Дополнительные полезные команды

Переименовать файл

Переименовывает или перемещает tracked-файл и сразу добавляет это изменение в staging. Git всё равно определяет rename по содержимому, но git mv делает операцию удобнее.

git mv old.txt new.txt

Удалить tracked-файл

Удаляет tracked-файл из рабочей копии и одновременно добавляет его удаление в staging. После следующего commit файл исчезнет из этой версии репозитория.

git rm path/to/file

Перенести один commit

Берёт изменения одного указанного commit и применяет их поверх текущей ветки, создавая новый commit. Полезно, когда нужен конкретный fix без merge всей исходной ветки.

git cherry-pick <commit>

Прервать cherry-pick

Отменяет незавершённый cherry-pick и пытается вернуть состояние, которое было до начала операции. Используйте при сложных конфликтах или если выбрали не тот commit.

git cherry-pick --abort

Кто отслеживает файл?

Проверяет, находится ли указанный путь среди файлов, которые Git отслеживает в index. Если команда ничего не вывела, путь обычно не является tracked.

git ls-files path/to/file

Тип объекта Git

Показывает тип Git-объекта по его HASH: commit, tree, blob или tag. Это низкоуровневая диагностическая команда для понимания внутренней структуры репозитория.

git cat-file -t <HASH>

18. Готовые рабочие сценарии

Обычная работа

  1. Получить изменения:
    git pull --rebase
  2. Проверить состояние:
    git status -sb
  3. Посмотреть изменения:
    git diff
  4. Подготовить:
    git add -A
  5. Проверить staged:
    git diff --staged
  6. Commit:
    git commit -m "Описание изменения"
  7. Push:
    git push

Новая feature-ветка

  1. Обновить main:
    git switch main git pull --rebase
  2. Создать ветку:
    git switch -c feature/my-feature
  3. Commit:
    git add -A git commit -m "Add my feature"
  4. Опубликовать:
    git push -u origin feature/my-feature

Разрешить merge-конфликт

  1. Найти конфликтующие файлы:
    git diff --name-only --diff-filter=U
  2. Исправить файлы вручную и удалить маркеры конфликта.
  3. Отметить решёнными:
    git add path/to/file
  4. Завершить:
    git commit

После rebase обновить опубликованную ветку

  1. Проверить историю:
    git log --oneline --graph --decorate -20
  2. Обновить remote:
    git push --force-with-lease
Не используйте --force без необходимости.

Вернуть потерянный commit

  1. Найти:
    git reflog
  2. Проверить:
    git show HASH
  3. Создать recovery-ветку:
    git switch -c recovery HASH

Временно переключиться на другую задачу

  1. Спрятать работу:
    git stash push -u -m "WIP: текущая задача"
  2. Переключиться:
    git switch main
  3. Вернуться:
    git switch feature/my-feature git stash pop

19. Минимум, который стоит запомнить

Минимальный набор

git status -sb git diff git diff --staged git add -A git commit -m "message" git log --oneline --graph --decorate --all git switch -c feature/name git switch main git branch --show-current git branch -m new-name git fetch --prune git pull --rebase git push git push --force-with-lease git restore --staged file git restore file git revert HASH git reflog git stash push -u -m "WIP" git check-ignore -v path/to/file git remote -v
Перед опасными операциями: git status, git diff, git log/reflog. Если работа ценна — сначала commit или stash.
